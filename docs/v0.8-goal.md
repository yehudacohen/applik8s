implementation goal. It is intentionally concise: live progress belongs in the
execution plan's Current execution cursor and reconciliation ledger, not in a
second stale history embedded in the prompt.

release definition. Read it completely before acting, including its Current

Resume protocol

1. Inspect the exact branch, dirty worktree, recent commits, running processes,
   Current execution cursor, reconciliation ledger, and active evidence row.
2. Preserve every intentional edit and user-owned untracked file. Never reset,
   overwrite, or merge a stale branch wholesale, and never port patched `dist`
   files.
3. Reproduce the smallest regression for the one bounded cutover already in
   progress. Finish, truthfully block, or checkpoint it before opening another
   writer, migration, or execution-family cutover.
4. Run focused evidence first, then affected package, clean-consumer,
   generated-artifact, browser, Docker, OrbStack, MiniStack, migration, security,
   performance, and cost gates in proportion to the claim.
5. Update the exact evidence row and operational cursor, then commit the bounded
   slice before beginning the next one. Keep an implementation change and its
   evidence reconstructible.
6. At each milestone, produce the execution plan's release burn-down and select
   the smallest prerequisite on the remaining critical path.

Required architecture and sequence

- Follow the execution plan's priority order: P0 integrity and authority
  correctness, then P1 execution-model convergence, then P2 provider breadth and
  maturity claims. Independent characterization may proceed in parallel, but a
  later lane must not recreate an unfinished signer, serializer, admission,
  credential, scheduling, or lifecycle authority.
- Preserve one semantic application graph and derive deterministic, redacted,
  target-specific plans from it. Unsupported target semantics fail before
  mutation with stable compatibility diagnostics.
- Finish Runtime Integrity rather than recreating it: one Canonical JSON v1
  algebra with named domain policies and explicit TypeKro/CEL/reference adapters;
  one portable, purpose-separated signed-envelope substrate with Node and
  WebCrypto implementations; and one validated canonical admission context with
  narrowed execution-family views.
- Share mechanics without erasing domain meaning. Command, query, stream,
  workflow, actor, search, object-storage, and other payload schemas, authority,
  lifecycle, and public errors remain domain-owned. Cross-purpose envelope use
  must fail.
- Complete callable provider injection. `application.inject()` returns typed
  callable handles whose implementation, qualification, credentials, readiness,
  private dependencies, access, and topology remain framework-managed. Direct
  calls, stable extracted operations, module-local helpers, and clean external
  packages must preserve the same dependency metadata across every maintained
  execution family.
- Complete function-native scheduling convergence only where semantics match.
  `schedule(parameters, closure)` is the golden path; compatible workflow cron
  and delayed execution lower through the shared definition/instance/occurrence
  graph. Processor lifecycle, actor alarms, and raw infrastructure cron retain
  their distinct authorities. Never approximate cadence, precision, timezone,
  overlap, misfire, retry, cancellation, or history semantics.
- Complete actor authority and distributed qualification, including causal
  identity, fencing, cancellation, alarms, relocation, restart, rollout,
  resource-loss repair, realtime reconnection, and leak-free teardown.
- Complete graph planning, inferred runtime access, local runtime,
  observability, lakehouse, target parity, developer agent, migration/security,
  performance/cost, product acceptance, and exact-candidate review through the
  work packages and dependency graph in the execution plan.
- Consolidate mechanics without erasing domains. Typed payloads, authorization,
  lifecycle, retry/cancellation, cursor/checkpoint behavior, and public errors
  remain owned by their execution family. Different Canonical JSON policies use
  explicit adapters; processor timers, actor alarms, workflow durability, and
  infrastructure cron remain distinct unless the scheduling matrix proves exact
  equivalence. Do not measure success by file, line, or package count.
- Keep GuestBook, Chirp, and Agentic Start as the only in-repository acceptance
  applications. Downstream products are separate dogfooding consumers. Produce
  only the provider-neutral validation handoff defined by the plan; do not add
  downstream names, source, schemas, migrations, product workflows, confidential
  architecture, or product-specific release gates to this repository.

Completion and evidence discipline

- Use the plan's evidence states exactly: `not-started`, `characterized`,
  `implemented`, `integrated`, `live-qualified`, `externally-blocked`, and
  `rejected`. Deterministic evidence never substitutes for live qualification.
- Keep evidence state separate from `release-required`, `claim-required`, and
  `non-gating`. An external blocker does not waive a release requirement or make
  a target claim pass.
- In milestone burn-downs, classify remaining work as mechanism, migration,
  qualification, maintained-product, or downstream-only validation. Select the
  earliest blocking dependency rather than optimizing a broad completion
  percentage.
- Every public or persisted change records its compatibility class, readers,
  writers, lifetime, migration phase, rollback boundary, telemetry, owner, and
  removal condition. Use the plan's rolling durable-format migration unless exact
  lifetime evidence proves a narrower safe transition.
- Maintain one canonical authority per capability. Telemetry is evidence,
  provider metadata is not admission, provider process identity is not actor
  identity, and target plans are derived rather than independent authorities.
- Close the named source inventories. Maintained execution packages must not
  regain private cryptographic envelope mechanics, lookalike canonical JSON,
  private admission shapes, internal provider-runtime imports, ambient
  credentials, or parallel scheduling adapters.
- Require a consolidation cutover proof before widening shared machinery:
  characterize the existing bytes and behavior first, migrate one named consumer
  cohort, preserve a public golden-path fixture, close the relevant source gate,
  and either delete the old implementation in the same slice or register its
  bounded compatibility reader. Do not create a public abstraction that cannot
  name the first code it replaces.
- For each canonical-value, signed-envelope, admission, or scheduling cutover,
  use the execution plan's convergence seam contract. Name the canonical owner,
  the semantics that remain domain-owned, the first bounded consumer cohort, the
  exact old code removed or retained reader registered, and the proof that
  permits the next cohort to start. A shared helper without that semantic cutover
  is not completion.
- Review every consolidation cutover for singular ownership, domain semantic
  parity, retained-state and rollback safety, deletion or bounded registration of
  superseded code, preserved clean-consumer developer experience, and
  operationally truthful diagnostics and evidence. Moving callers behind a
  helper or passing unit tests does not by itself complete a cutover.
- Close the four observed duplication families to their concrete end states:
  private cryptographic mechanics disappear behind the purpose-separated signed
  envelope substrate; every canonical byte producer names a Canonical JSON v1
  policy or explicit reference adapter; every maintained ingress constructs the
  canonical admission context only after its own transport proof; and every
  scheduling surface has an executable `lower`, `preserve`, or `reject`
  disposition. `pending-migration` is not completion.
- Preserve package architecture while consolidating. Move only portable bytes,
  validation, signing, and verification mechanics into focused lower-level
  subpaths. Keep typed payloads, authorization, lifecycle, idempotency,
  checkpointing, provider behavior, and public errors domain-owned. Reject a
  cleanup that introduces dependency cycles, broad umbrella imports, or a
  framework god package merely to reduce file or line count.
- Prove the requirement-to-evidence join: RFP requirement -> scorecard pillar ->
  classified acceptance gate -> work package -> qualifying commit -> checked-in
  evidence packet -> command/artifact/environment/cleanup receipt.
- Preserve the authored developer experience. Internal consolidation must not
  force application authors to supply serializers, signers, admission wrappers,
  credentials, target branches, provider-runtime imports, or scheduling adapters.
  Any public API change must be required by an accepted contract or maintained
  acceptance failure, and must be simpler than what it replaces.
- AWS-local is API-fidelity evidence only. Do not claim real AWS, IAM,
  CloudWatch, Athena, EventBridge Scheduler, networking, encryption, lifecycle,
  performance, or cost maturity without the exact real-environment receipt.
- Live tests require bounded preflight, ownership proof, lifecycle-aware
  Applik8s/Alchemy/TypeKro teardown, and verified absence. A cleanup leak fails
  the gate; raw Kubernetes deletion is emergency repair evidence, not normal
  lifecycle.

Authority and safety

Continue autonomously for implementation decisions that preserve the accepted
contract. Ask only before narrowing or removing an accepted stable claim,
weakening security/authority/tenancy/durability/lifecycle, adopting a destructive
or non-rollback-safe migration, inventing a genuinely new public execution
concept, publishing or releasing, or mutating production. A missing decision
blocks only its dependent lane; continue independent work.

Do not read, print, overwrite, or commit `.env` files or secrets. Do not delete or
commit user-owned untracked files. Do not tag, publish packages or images, create
a GitHub Release, deploy to production, rewrite history, or retry an external
push without explicit maintainer authorization.

Finish by assembling—but not publishing—the exact-candidate maintainer packet
defined by `RQ-1`, with every claim stated at the weakest truthful evidence level.
