**Scope:** Corrections proven on the supported v0.7 line, current v0.8

## Outcome

Incorporate the corrections and reusable lessons without importing downstream
patches wholesale, weakening the function-native programming model, or turning
Agentic Start into a generic collection of product screens.

The resulting state should have four properties:

1. applications promoted from v0.7 preserve their model, schema, workflow, and
   authority semantics without local patches;
2. generated applications can accept semantic Start upgrades without losing
   application-owned edits;
3. Agentic Start demonstrates both interactive and durable agent execution,
   governed publication, truthful work products, cost evidence, and operational
   ownership through normal Applik8s primitives; and
4. application-specific navigation, product journeys, objectives, and runbooks
   remain easy to own and extend in generated source.

## Incorporation principles

1. **Port behavior, not patches.** Compare each compatibility change with the
   current v0.8 implementation, retain only the missing semantics, and delete or
   retire the downstream patch once packed-package evidence passes.
2. **Keep domain meaning in the application.** Documents, reviews, agents,
   navigation, objectives, and journeys may be generated application source.
   Protocols, provider lifecycles, authority, accounting, persistence, and
   upgrade mechanics belong in maintained packages.
3. **Prefer extension seams to hidden configuration.** A generated application
   should edit ordinary typed source for its product home, navigation,
   objectives, runbooks, tools, and providers. Framework complexity stays behind
   public primitives; product meaning does not.
4. **Preserve two legitimate agent shapes.** Interactive assistants use the
   maintained conversational agent loop. Durable or background specialists run
   inside admitted task/workflow execution and may call inference and typed
   operations without being forced through the conversational facade.
5. **Authoritative outcomes are server-authored.** A model may propose content,
   but identity, provenance, receipts, terminal state, cost, and publication
   evidence come from admitted framework execution.
6. **Unknown never becomes healthy.** Deterministic fixtures, provider status,
   evaluation state, and operational views must distinguish absent evidence,
   insufficient evidence, degraded service, and verified success.
7. **No default-template bloat without a journey.** A new generated file or
   dependency must participate in an understandable product journey or provide
   an intentional application extension point.

### Retain as application-owned examples, not shared framework modules

The following are useful patterns, but their meaning belongs in generated
application source:

- product-specific Documents and review policy;
- the exact Inbox taxonomy and decision presentation;
- agent instructions, tool grants, datasets, scorers, publication thresholds,
  and rollback policy;
- product navigation, home journey, operational objectives, thresholds,
  runbooks, and ownership labels; and
- product-specific specialist topology and work-product schemas.

Shared packages may provide primitives and generic views. They must not own
these policies merely because more than one application can imagine them.

### Do not incorporate

Do not move customer-zero domain semantics into Applik8s, including source
acquisition policy, domain-specific retrieval and canonicalization, governed
network threat policy, contributor-network semantics, delivery semantics,
domain accounting interpretations, or product-specific retention thresholds.

## Execution sequence

### Phase 0 — Reconcile before editing

1. Build a machine-readable inventory of every supported-line patch and
   customer-zero workaround.
2. Classify each as `already-integrated`, `missing`, `superseded`, or
   `application-owned` against the exact v0.8 head.
3. Add a focused reproduction before porting a `missing` behavior.
4. Update the reconciliation ledger; do not carry stale patch claims forward.

Exit: every known correction has one disposition and no downstream patch is
treated as authoritative source.

### Phase 1 — Close compatibility correctness

Implement `COMPAT-1` through `COMPAT-4`, then audit and conditionally implement
`COMPAT-5` and `COMPAT-6`. Run focused package tests first, followed by generated
dispatch, packed clean-consumer, PostgreSQL, workflow-provider, authority, and
security gates.

Exit: the supported customer-zero application can remove the corresponding
package patches and typecheck against packed v0.8 packages. Downstream product
acceptance is coordinated separately and is not itself an Applik8s release gate.

### Phase 2 — Make Start upgrades safe

Implement `START-1` before broad template edits. Store the base template digest
and reviewable per-file ownership in tracked state. Reconstruct the exact base
from the recorded generator package/version and generation inputs, verify its
digest, then compare base/current/new and produce a deterministic update plan.
If the exact base cannot be reconstructed, fail closed and accept an explicit
verified base artifact; do not guess from the current file. Never overwrite an
application-edited file automatically when both application and upstream
changed it.

Exit: all later starter changes can be applied to a generated v0.7 project with
an explicit semantic report and no lost application edits.

### Phase 3 — Establish application extension seams

Implement `START-2` through `START-4`: typed navigation contributions, an
application-owned home journey, and operational objectives/runbooks composed
with maintained generic surfaces. Split generated organization where needed,
but do not add a runtime configuration DSL.

Exit: a generated fixture adds a product route, builder route, operational
objective, and runbook through ordinary typed source; desktop/mobile/SSR and
authority behavior remain correct.

### Phase 4 — Demonstrate trustworthy agentic execution

Implement `START-5` through `START-7` and retain `START-8` as a permanent
acceptance journey: interactive plus durable specialist execution, named logical
inference roles, server-authored work products, and governed agent release.
Reuse existing workflow, task, model, evaluation, artifact, and authority
primitives; introduce no public `operation()` ceremony.

Exit: a user can configure, ground, grant, evaluate, publish, invoke, observe,
review, and roll back one exact agent revision. A durable specialist can restart
without duplicating its authoritative result.

### Phase 5 — Make economics and external evidence honest

Implement `START-9` through `START-11`: provider-accounting presentation,
truthful deterministic fixtures, and an opt-in Web research journey.

Exit: Usage and run details agree with authoritative provider records; absent
pricing or evidence is explicit; the credential-free lane remains mandatory;
the live research lane is additive and never fabricates a release pass.

### Phase 6 — Exact-candidate qualification

At one exact commit:

1. generate a fresh product application and a v0.7-to-v0.8 update fixture;
2. run workspace typecheck, lint, documentation, module-boundary, package
   consumer, and generated-tree cleanliness gates;
3. run the mandatory credential-free browser journey across supported browsers;
4. run PostgreSQL, workflow restart, specialist idempotency, authority,
   provider-accounting, and Operations evidence paths;
5. run opt-in live inference, Web search, payments, and notification lanes only
   when their credentials are explicitly supplied;
6. deploy the generated application through the normal graph, prove a no-change
   reapply and one update, and destroy it through managed topology; and
7. record the exact source commit, package digests, generated lineage, artifacts,
   environment, limitations, and cleanup receipt in the main ledger.

## Release-blocker boundary

The following block v0.8:

- reproduced `COMPAT-1` through `COMPAT-4` defects;
- a reproduced `COMPAT-5` or `COMPAT-6` defect;
- unsafe or destructive generated-source upgrade behavior after `START-1` is
  exposed as a supported command;
- either agent execution shape bypassing admission, causal identity,
  idempotency, authority, or authoritative result ownership;
- generated UI presenting missing provider, evaluation, pricing, or operations
  evidence as healthy or complete;
- a mandatory credential-free product journey failure; or
- failed managed deployment/update/teardown of the exact generated candidate.

The following may remain opt-in or explicitly limited without blocking v0.8:

- live third-party inference, payments, notifications, and public Web search
  when credentials or external service availability are absent;
- generic durable clarification beyond the already-supported review/signal
  journey;
- a universal agent-governance product independent of generated application
  policy; and
- downstream product-specific validation.
