# v0.8 runtime-access materializer inventory

Status: active `RA-1c1` characterization. This document records code paths and
gaps; it is not qualification evidence.

## Canonical source

`compileApplicationRuntimeAccessPlan()` is the only semantic policy compiler. It
derives source-attributed requirements, intersects selected provider guarantees,
and emits exact local, Kubernetes, and AWS lowerings per execution identity.

The target-neutral enforcement envelope introduced by `RA-1c1` must be a
portable projection of that plan. Target code may translate provider limits, but
must never re-derive semantic authority from application nodes, environment
variables, or already-emitted resources.

## Current consumers

| Target/path | Current behavior | Gap to close |
| --- | --- | --- |
| Local supervisor | Compiler artifacts retain exact framework credentials; the CLI validates them and each child receives only its declared subset. Provider bindings are still lowered from graph/provider configuration. | Bind the complete runtime-access policy digest to the supervisor plan and prove every materialized provider binding has one canonical requirement. |
| Kubernetes deployment graph | `compileApplicationDeploymentGraph()` computes and returns a runtime-access plan beside the deployment graph. `emitApplicationDeploymentGraph()` serializes only the graph and later recomputes the semantic ApplicationPlan. | The effect-owning deployment graph does not carry the policy it must enforce. TypeKro/Alchemy can deploy without proving RBAC, NetworkPolicy, and Secret projection parity. |
| Generated Kubernetes workloads | HTTP, agents, workflows, processors, reactive runtimes, MCP, lakehouse publishers, operators, and the ApplicationHost independently emit ServiceAccounts, RBAC, NetworkPolicies, and Secret-backed environment entries. | These are useful target implementations but currently act as independent policy authors. Their output must be checked against—not treated as a substitute for—the canonical enforcement envelope. |
| Kubernetes Secret access | Semantic `secret.read` currently lowers to both named-Secret RBAC and `kubernetes-secret-projection`. Most generated Node workloads receive the Secret through a pod environment/volume projection and do not call the Kubernetes Secret API. | The enforcement envelope must distinguish kubelet projection from API read so least privilege does not grant an unused `get secrets` permission. Ambiguous access must fail closed. |
| AWS plan compiler | `compileApplicationAwsDeploymentPlan()` recomputes runtime access, creates one IAM role per execution, then selects a role for a runtime artifact by semantic `nodeId`. Additional database, checkpoint, schedule, and runtime-secret statements are appended through separate graph-derived paths. | One artifact can silently select the first matching role, and ad hoc statements are not joined back to requirement IDs. Every task role and security-group edge must be produced from or justified against one canonical envelope. |
| AWS deployment contract and Alchemy | The AWS plan persists IAM resources and ECS role references. CloudFormation faithfully renders those resources. | The persisted plan omits the runtime-access envelope/digest, so validation and apply cannot prove that IAM/network/secret materialization is complete, non-widened, and bound to the intended workload. |

## `RA-1c1` implementation boundary

1. Add a versioned, portable runtime-access enforcement envelope to
   `@applik8s/deployment-contract`. It contains target, source graph digest,
   policy digest, execution/node identities, requirement IDs, mechanisms, and
   target identities; it contains no credentials.
2. Embed that envelope in the Kubernetes deployment graph and AWS deployment
   plan. Validation rejects a missing envelope, target mismatch, graph mismatch,
   duplicate execution ownership, wildcard grant, unresolved error diagnostic,
   or digest mismatch before an effect runner is invoked.
3. Add one parity validator per target. It joins materialized ServiceAccounts,
   RBAC, NetworkPolicies, Secret projections, IAM roles, task-role references,
   and network edges back to envelope executions and requirement IDs.
4. Replace AWS's first-role-by-node lookup and separate statement appenders with
   an explicit workload enforcement record. Reject multiple execution policies
   unless their union is deliberate, deterministic, and recorded on that exact
   workload.
5. Make Kubernetes projection versus API-read semantics explicit before
   materializing Secret access. Do not retain unused Secret RBAC merely because
   an environment projection exists.

## Required deterministic evidence

- the same source graph and selected provider guarantees produce byte-identical
  enforcement envelopes across repeated compilation;
- removing, widening, or misbinding one Kubernetes rule, NetworkPolicy edge,
  Secret projection, AWS statement, role attachment, or security-group edge
  fails before mutation with the requirement and execution identity;
- two executions on one semantic node cannot make a workload select an arbitrary
  first role or ServiceAccount;
- a sibling runtime receives neither another runtime's credential projection nor
  its role/network authority;
- unsupported provider guarantees and target ceilings remain named diagnostics,
  not synthetic wildcard grants;
- the envelope, deployment graph/AWS plan, and ApplicationPlan share the same
  source-graph and policy digests.

## Evidence boundary

Passing `RA-1c1` proves deterministic target lowering and pre-mutation refusal.
It does not prove Kubernetes admission/denial, IAM behavior, security-group
behavior, drift repair, or production credentials. Those remain `RA-1c2`,
`RA-1c3`, and `RA-1d` claims with independently labelled live evidence.
