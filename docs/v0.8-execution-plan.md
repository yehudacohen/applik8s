# Applik8s v0.8 execution plan

**Status:** Accepted implementation sequence

**Scope:** Applik8s source, packages, generated applications, maintained providers,
and release evidence. Downstream consumer validation is coordinated separately and
is not an Applik8s release gate.

**Release boundary:** Do not tag, publish packages or images, create a GitHub
Release, or deploy to a production environment without explicit maintainer
authorization.

## Outcome

Deliver the complete v0.8 manifesto through one semantic application graph, one
authority and admission model, one dependency-injection model, one canonical
serialization foundation, and target-specific provider lowerings for local,
AWS-local, AWS, and Kubernetes.

The program must preserve the substantial implementation already present while
removing duplicated security and serialization machinery before it becomes a
permanent cross-runtime contract.

## Non-negotiable principles

- Checkpoint unique work before rebasing, deduplicating, or changing history.
- Implement retained fixes in canonical source. Never port patched `dist` files.
- Keep the narrow v0.7.x HTTP-to-workflow unblock separate from the larger v0.8
  refactor.
- Canonical JSON bytes are defined before signatures and digests depend on them.
- Domain-specific cursor and token payloads remain distinct while sharing one
  signed-envelope substrate.
- Identity admission is normalized once; execution families consume narrowed
  views and retain their own operation authorization.
- Provider selection, credentials, readiness, topology, and private runtime
  dependencies remain framework-managed.
- Actor alarms remain actor timers. They are not application schedules.
- AWS-local proves API fidelity only. It never substitutes for real-AWS evidence.
- GuestBook, Chirp, and Agentic Start are the in-repository acceptance
  applications. Downstream products are dogfooding consumers, not release gates.
- v0.8 is an implementation-and-convergence release. Do not invent unrelated
  public capability while closing its accepted contracts. A new API is allowed
  only when an accepted RFP requires it or an acceptance application proves that
  the existing shape cannot express the required behavior.
- Compatibility is explicit rather than accidental. Every public or persisted
  contract change names its compatibility class, migration owner, rollback
  boundary, and removal release before implementation is considered complete.

## Program control and evidence states

Every ledger row and implementation slice uses one of these evidence states. The
machine-readable acceptance manifest retains its conservative `implemented`
boolean: it stays `false` until the gate's required integrated and live evidence
has passed.

- `not-started`: no canonical implementation exists;
- `characterized`: the current behavior and failing regression are recorded;
- `implemented`: canonical source and deterministic tests pass;
- `integrated`: all affected packages, generators, and maintained providers pass;
- `live-qualified`: the exact required environment passed with verified cleanup;
- `externally-blocked`: implementation is complete but named external evidence is
  unavailable; or
- `rejected`: the proposed behavior was deliberately excluded with rationale and
  regression protection.

`implemented` never implies `live-qualified`. Documentation and scorecard flags
must use the weakest truthful state. Each transition records the exact commit,
command, environment, evidence artifact, and cleanup result.

## Definition of done for every implementation slice

A slice is complete only when all applicable items are satisfied:

1. The canonical source owner contains the implementation; generated output and
   patched `dist` files are never the source of truth.
2. Public types, runtime behavior, compiler lowering, generated source, package
   exports, and dependency manifests agree.
3. Positive, negative, adversarial, migration, and cleanup regressions exist in
   proportion to the risk.
4. Focused tests, affected package typechecks, formatting, and diff checks pass;
   broad gates run at the integration boundary rather than after every edit.
5. Clean packed-consumer evidence proves that undeclared workspace hoisting does
   not mask dependency or export defects.
6. Documentation shows the intended golden path and removes or labels obsolete
   syntax.
7. Persisted-format or authority changes include mixed-version, rollback, and
   failure-interruption evidence.
8. Live tests perform bounded preflight and leak-free lifecycle cleanup when a
   live environment is part of the maturity claim.
9. The reconciliation ledger and machine-readable scorecard are updated with no
   stronger claim than the evidence supports.

## Dependency lanes

The program is a dependency graph, not one serial queue:

```text
checkpoint + reconciliation
  -> release-line HTTP/workflow fix
  -> v0.8 rebase
      -> Canonical JSON v1
          -> signed envelopes
              -> canonical admission
                  -> callable provider injection
                  -> scheduling convergence
                  -> actor authority completion

after canonical admission:
  provider injection ----> target/provider parity ----> product acceptance
  scheduling ------------> local/Kubernetes/AWS evidence ------^
  actors ----------------> distributed lifecycle evidence ------^
  runtime integrity -----> migration/security/performance ------^
```

Work in separate lanes may proceed concurrently only when it does not duplicate
an unfinished foundation. Canonical JSON precedes signatures; signed envelopes
precede admission token migration; canonical admission precedes new ingress
lowerings. Product applications may characterize gaps throughout, but their
release evidence is rerun only after the affected foundations integrate.

## Phase 0 — secure the current implementation

1. Checkpoint the complete dirty v0.8 worktree in reviewable commits and push the
   branch.
2. Record current passing gates, external blockers, and known failures without
   converting candidate evidence into release claims.
3. Preserve the successful actor contract suite and distributed celld lifecycle.
4. Record the Kubernetes actor failure as OrbStack pod-capacity exhaustion; its
   Alchemy teardown succeeded and its live qualification remains unearned.
5. Create a reconciliation ledger mapping each known finding to its source fix,
   regression test, release-line commit, v0.8 commit, and downstream patch-removal
   condition.

Slice the checkpoint by coherent ownership boundary—planning/contracts,
local/AWS targets, schedules, observability/lakehouse, actors, development
environment/product, and evidence—without rewriting or discarding cross-cutting
work merely to create artificial commit purity. Record each commit and uncommitted
exception in the ledger before rebasing.

The ledger is a checked-in machine-readable or Markdown table with these required
columns: finding, originating worktree/patch, canonical source owner, regression
command, release-line disposition, v0.8 disposition, migration requirement, and
removal condition.

**Exit:** No unique implementation exists only in an uncommitted or unidentified
worktree.

## Phase 1 — narrow v0.7.x HTTP-to-workflow unblock

Reconcile the maintained v0.7.x release work with the focused HTTP-workflow branch
without importing the wider v0.8 program.

- Discover statically named workflow calls as semantic bindings.
- Inject provider-neutral run/start handles into generated typed HTTP handlers.
- Do not import or register authored workflow/task modules inside the HTTP image.
- Attach the selected workflow engine, credentials, readiness, and network policy.
- Preserve request-derived idempotency, principal, trusted context, correlation,
  causation, cancellation, bounded observation, and lost-response reattachment.
- Reject undeclared or dynamically selected workflow identities.
- Prove that losing an HTTP response and retrying produces one admitted workflow
  run and one effect path.

This phase may be released independently after review. It must not wait for the
v0.8 runtime-integrity refactor.

**Exit:** One reviewed release-line implementation and an exact regression test
exist for typed HTTP-to-workflow invocation. The candidate also passes clean
packed-consumer generation and an emitted-worker retry/reattachment test. If live
Hatchet evidence is unavailable, the branch remains independently reviewable but
is not described as live-qualified.

## Phase 2 — rebase and reconcile v0.8

1. Rebase the checkpointed v0.8 branch onto the authoritative v0.7.x release-line
   tip.
2. Port the focused HTTP-workflow fix and remove independently duplicated
   implementations.
3. Inspect older worktrees only for unique changes; do not merge stale branches
   wholesale.
4. Inventory downstream compatibility patches and map every one to canonical
   source and tests.
5. Preserve generated package discovery, search dependencies, schema behavior,
   provider capture, and fresh-cluster evidence fixes already accepted on the
   release line.

**Exit:** Every retained finding has one canonical implementation and test.

## Phase 3 — runtime integrity foundation

Runtime integrity is a stable, cross-cutting v0.8 release requirement. Amend the
manifesto, scorecard, acceptance manifest, package boundaries, and release gates
with executable evidence as each section lands.

The normative contract is
[`rfp-v08-runtime-integrity.md`](rfp-v08-runtime-integrity.md), and package
dependency direction is fixed by
[`adr-v08-runtime-integrity-package-ownership.md`](adr-v08-runtime-integrity-package-ownership.md).
The `runtime-integrity` scorecard gate remains `implemented: false` until its
canonical implementation, fixed vectors, source inventory, and rolling-migration
evidence all pass.

### 3A. Canonical JSON v1

Define one platform-neutral and explicitly versioned canonical JSON algebra.
Named domain policies must cover:

- deterministic object-key ordering;
- `undefined` in objects and arrays;
- root `null`;
- finite numbers and negative zero;
- cycles and repeated references;
- unsupported runtime values;
- strings and byte representations; and
- TypeKro/CEL references through explicit adapters.

Migrate graph, deployment, compiler, client, workflow, schedule, actor, search,
and lakehouse digests onto named policies over this algebra. Fail closed when a
domain cannot be represented rather than silently choosing another policy.

### 3B. Versioned signed envelopes

Create one portable signed-envelope contract with:

- explicit purpose/audience separation;
- format version and algorithm;
- key identity;
- issuance and expiry;
- typed payload validation;
- encoded-size bounds;
- constant-time verification;
- Node and WebCrypto adapters;
- structured errors; and
- key-rotation support.

Commands, queries, subscriptions, tasks, object storage, search, celld tickets,
and lakehouse cursors keep distinct payload schemas. They share canonical bytes,
base64url handling, signing, verification, expiry, and error behavior.

Give deterministic, PostgreSQL, and OpenSearch providers one shared search cursor
codec. Providers contribute only provider-specific continuation state.

### 3C. Canonical admission context

Define one framework-produced and validated admission context containing:

- authenticated principal;
- authority revision;
- trusted-context values and digest;
- authorization receipt where required;
- operation and transport identity;
- correlation and causation;
- deadline and cancellation; and
- trace context.

The request identity boundary constructs and validates it once. HTTP, commands,
queries, subscriptions, processors, workflows, schedules, actors, agents, and AI
consume narrowed views. Their application authorization remains independent.

Admission construction must cover every maintained ingress explicitly:

- authenticated HTTP and browser/SSE requests;
- verified webhooks and provider callbacks;
- broker deliveries;
- workflow and task deliveries;
- schedule occurrences using a bounded scheduler service principal;
- actor calls and persisted alarm authority; and
- named framework service principals.

Each adapter verifies transport-specific evidence and produces the canonical
context. None may fabricate a human identity, reuse the principal that configured
a later schedule, or define another principal/trusted-context structure.

Maintain `docs/v0.8-admission-adapter-matrix.json` as the executable inventory for
this convergence. Every row names the evidence verifier, principal source,
operation-identity rule, transport, implementation state, regression command, and
remaining work. The parity gate enumerates this file and fails when a maintained
ingress is absent, when an implemented row lacks a regression, or when source
inventory finds a private principal/authority/trusted-context admission shape.
Adding an ingress therefore requires adding its canonical adapter and matrix row
in the same slice; prose-only coverage is not sufficient.

### 3D. Migration and evidence

- New versions emit only canonical v1 formats.
- Add an explicit bounded legacy decoder only where a durable released token can
  legitimately outlive deployment; never silently try multiple purposes.
- Add shared fixed vectors across Node, browser, WASM, worker, compiler, and
  provider runtimes.
- Prove cross-purpose substitution, tampering, expiry, truncation, wrong keys,
  oversized payloads, malformed canonical input, and ambiguous adapters fail
  closed.
- Add a source-level gate that prevents maintained gateways and providers from
  reintroducing private HMAC/base64url implementations or parallel admission
  context shapes.

Classify every persisted token or record as request-local, resumable/expiring, or
durable. Durable rolling migrations use read-legacy-and-v1/write-legacy,
read-legacy-and-v1/write-v1, then read-v1-only releases unless an exact migration
record proves that mixed readers and writers cannot coexist. A legacy decoder has
an owner, maximum lifetime or retained-state proof, telemetry, and removal release.

Maintain `docs/v0.8-format-registry.json` as the checked-in registry for every
signed envelope, cursor, digest, admission record, deployment artifact, and
durable runtime record. Each entry names its writer versions, reader versions,
maximum lifetime, migration phase, key/purpose namespace, telemetry, rollback-safe
release, and decoder-removal release. Upgrade tests must be restart-safe at every
committed migration boundary; rollback tests must prove that the documented
previous version can still read all state written during the rollback window.

**Exit:** Maintained gateways/providers contain no independent cryptographic
envelope implementation, canonical bytes agree across runtimes, and admission has
one authoritative validator.

## Phase 4 — callable provider injection

Adopt this golden path:

```ts
const provider = application.inject(
  AcquisitionProvider.named("primary"),
);

await provider.acquire(input);
```

Required semantics:

- `application.inject()` returns a typed callable provider handle/proxy, not an
  inert descriptor and not a live build-time client.
- The handle remains compiler-visible, serializable, and runtime-hydrated.
- Extracted operations are stable bound function handles; arbitrary JavaScript
  `this` behavior is not part of the contract.
- Qualification, target/profile selection, graph identity, credentials,
  readiness, network access, and topology are framework-managed.
- Provider-private stores, clients, cancellation state, and credentials are
  injected behind provider construction.
- Only workloads that use the provider receive its configuration and credentials.
- Captured or returned provider methods propagate their dependency through
  modules, HTTP handlers, operations, processors, tasks, workflows, schedules,
  actors, and generated workers.
- Portable package-authored metadata makes external compiled packages first-class
  compiler inputs without namespace privilege or application wrapper glue.
- Remove application imports of internal provider-runtime modules after the
  compatibility path is qualified.

**Exit:** Clean package consumers use callable injected providers through every
maintained execution family with exact dependency and credential lowering.

## Phase 5 — complete execution-family convergence

### Scheduling

- Make imported `schedule(parameters, closure)` the public golden path.
- Use one definition/instance/occurrence model for fixed, dynamic, recurring,
  immediate, and one-time execution.
- Lower compatible workflow crons and future task/workflow execution through the
  shared schedule graph.
- Keep processor schedule convergence internal.
- Keep raw Kubernetes image/command scheduling as an explicitly named
  infrastructure escape hatch.
- Qualify deterministic local, bounded Kubernetes, shared Hatchet, and EventBridge
  Scheduler providers against the same portable contract.

### Actors

- Close remaining external alarm-cancellation authority gaps.
- Preserve exact connection, message, nested call, and alarm authority.
- Qualify deploy, rolling update, pod loss, reassignment, state recovery, drift
  repair, realtime reconnection, alarm delivery, and lifecycle teardown.
- Rerun the Kubernetes actor lifecycle after safely removing stale project/test
  workloads that consume OrbStack capacity.
- Keep relational journals, immutable evidence, and workflow history authoritative
  where required by the domain.

**Exit:** Schedule and actor public APIs expose one coherent semantic model and at
least the providers required by their scorecard maturity have live evidence.

## Phase 6 — finish the v0.8 capability matrix

Complete and qualify the existing work rather than adding unrelated public APIs:

- canonical application plan and diff;
- inferred least-privilege runtime access;
- persistent local supervisor and independent development environment;
- provider-neutral OpenTelemetry and target-native exporters;
- immutable lakehouse publication and queries;
- local, Kubernetes, AWS-local, and AWS deployment targets;
- TypeKro/Alchemy dependency and lifecycle ownership;
- target-selected provider guarantees; and
- migration, security, performance, cost, and failure diagnostics.

Every target consumes the same semantic graph. Differences live in provider
guarantees and lowerings, not domain-source branches.

### Performance, scale, and cost budgets

Record reproducible baselines before optimizing and preserve history as evidence,
not as a one-off release note. The scorecard must define explicit ceilings or
regression percentages for:

- compiler wall time and peak memory for GuestBook, Chirp, and Agentic Start;
- generated JavaScript, WASM component, operator image, and browser bundle size;
- cold start and steady-state handler latency;
- bounded-concurrency throughput and backpressure behavior;
- database connection/pool pressure and durable-store contention;
- stream consumer scaling, retries, and redelivery;
- local supervisor idle/active memory;
- Kubernetes steady-state requests/limits; and
- representative AWS plan and observed test-fixture cost.

A regression beyond an accepted budget blocks the relevant maturity claim unless
the maintainer accepts a documented tradeoff. Performance gates use fixed fixtures,
warmup rules, multiple samples, and noise-tolerant statistics; a single timing
assertion is not release evidence.

Each workstream closes through the existing machine-readable gate rather than a
subjective phase-level declaration:

| Workstream | Required command | Required non-contract evidence |
| --- | --- | --- |
| Runtime integrity | `bun run check:v08:runtime-integrity` | Mixed-version fixture and cross-runtime fixed vectors |
| Graph and plan | `bun run check:v08:graph-provenance` and `bun run check:v08:application-plan` | Stable redacted artifacts from maintained acceptance applications |
| Local runtime | `bun run check:v08:local` | Fresh generated application, restart, crash recovery, reset, and teardown |
| AWS target | `bun run check:v08:aws-local` then `bun run check:v08:aws` | MiniStack API fidelity separately from real-AWS lifecycle/security/cost |
| Runtime access | `bun run check:v08:runtime-access` | Exact denied and allowed target policies without wildcards |
| Observability | `bun run check:v08:observability` | Local collector, Kubernetes backend, external OTLP, and real CloudWatch according to disposition |
| Scheduling | `bun run check:v08:scheduling` | OrbStack lifecycle and real EventBridge retry/DLQ evidence |
| Lakehouse | `bun run check:v08:lakehouse` | DuckDB plus real Athena/Glue/S3 lifecycle and cost evidence |
| Actors | `bun run check:v08:actors` | Distributed celld and Kubernetes lifecycle with leak-free teardown |
| Provider/target parity | `bun run check:v08:provider-conformance` and `bun run check:v08:target-parity` | One graph, target-specific plans, fail-closed incompatibility |
| Development environment | `bun run check:v08:development-agent` | Clean generated and intentionally broken application journeys |
| Migration/security/performance | `bun run check:v08:migration`, `bun run check:v08:security`, and `bun run check:v08:performance` | Retained-state upgrade, secret canaries, failure injection, and recorded history |
| Product | `bun run check:v08:product` | Browser, clean-consumer, production-bundle, and visual acceptance |

For each row, the reconciliation ledger records current state, exact remaining
work, responsible package boundary, command result, environment, cleanup result,
evidence artifact, and external blocker. An implemented flag changes only after
that row's exact command and required environments pass.

### Live-environment preflight

Before any long-running OrbStack, Docker, MiniStack, or cloud gate, run a bounded
preflight that verifies:

- expected context/account and explicit opt-in;
- node pod, CPU, memory, and storage capacity;
- required StorageClass, controllers, CRDs, and compatible versions;
- Docker, registry, image, network, and DNS availability;
- required provider configuration is present without printing secret values;
- absence of conflicting fixed-name test installations; and
- ownership metadata needed for lifecycle cleanup.

Preflight fails before mutation with actionable diagnostics. Cleanup uses the
owning Alchemy/TypeKro/application lifecycle and verifies absence; raw Kubernetes
deletion is emergency repair evidence, not the ordinary path.

## Phase 7 — product and example qualification

- **GuestBook:** readable minimum golden path.
- **Chirp:** distributed composition, streaming, access, object, lifecycle, and
  scale pressure.
- **Agentic Start:** polished product framework exercising identity, tenancy,
  billing, Stripe, usage, entitlements, search, agents, approvals, artifacts,
  evaluations, schedules, actors, and the Builder evidence surface.

Required evidence includes fresh generation, clean package consumption, local
startup/hot reload, browser journeys, production bundles, OrbStack deployment and
teardown, target plan parity, provider differential tests, generated-file
reproducibility, package boundaries, and bundle-size ceilings.

No internal package import may be required by generated application source.

## Phase 8 — release qualification

- Synchronize all coordinated package versions.
- Pass packed-consumer and published-shape import tests.
- Qualify generated runtime images and dependency/container provenance.
- Pass runtime-integrity, local, OrbStack, MiniStack, browser, migration,
  security, performance, cost, product, package, Rust, and scorecard gates.
- Run real AWS CloudWatch, Athena, EventBridge Scheduler, IAM, networking,
  encryption, drift, lifecycle, and cost evidence before claiming real-AWS
  compatibility.
- Keep scorecard and acceptance flags false until their exact commands and live
  environments pass.
- Produce a final gap analysis and exact-commit attestation for maintainer review.

The final maintainer packet contains:

- the exact source commit and coordinated package/image versions;
- public API additions, removals, and migration guidance;
- the format registry and rollback window;
- scorecard results with links to deterministic and live evidence;
- known limitations and externally blocked claims;
- performance/bundle/cost comparison against the recorded baseline;
- clean-install and previous-release upgrade results; and
- proof that all live test resources were removed.

Do not tag or publish until the maintainer separately authorizes the release.

## Critical path

```text
checkpoint
  -> narrow v0.7.x workflow unblock
  -> rebase and deduplicate
  -> canonical JSON v1
  -> signed envelopes
  -> canonical admission
  -> callable provider injection
  -> schedule and actor qualification
  -> remaining target/provider qualification
  -> product acceptance
  -> release review
```

This is the minimum blocking path. After canonical admission integrates, provider,
schedule, actor, target, migration, and product lanes should progress independently
and converge at release qualification.

## Evidence discipline

- A passing contract test is not live provider evidence.
- A successful MiniStack run is not real AWS evidence.
- A local actor provider is not distributed actor evidence.
- A generated plan is not a successful deployment.
- A preview UI cannot substitute for a stable runtime gate.
- Cleanup is part of every live lifecycle test and must fail on leaks.
- External blockers remain visible; they do not justify weakening maturity labels.
