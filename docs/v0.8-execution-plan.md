# Applik8s v0.8 execution plan

**Status:** Accepted implementation sequence

**Scope:** Applik8s source, packages, generated applications, maintained providers,
and release evidence. Downstream consumer validation is coordinated separately and
is not an Applik8s release gate.

**Release boundary:** Do not tag, publish packages or images, create a GitHub
Release, or deploy to a production environment without explicit maintainer
authorization.

## How to use this plan

This document is intentionally comprehensive, but it has three reading layers:

1. **Resume work:** read the Program completion contract, Current execution
   cursor, stop rules, and the active reconciliation/evidence rows.
2. **Review a slice:** read the relevant ownership map, work-package contract,
   phase detail, compatibility record, and required evidence packet.
3. **Review the release:** read the requirement classes, milestone burn-downs,
   requirement-to-evidence join, target claims, and exact-candidate checklist.

The concise copy/paste objective is [`v0.8-goal.md`](v0.8-goal.md). It contains
stable responsibilities and safety boundaries only. Current commits, failures,
and next commands belong here in the Current execution cursor and in
[`v0.8-reconciliation-ledger.md`](v0.8-reconciliation-ledger.md); do not copy
them back into the goal prompt.

## Outcome

Deliver the complete v0.8 manifesto through one semantic application graph, one
authority and admission model, one dependency-injection model, one canonical
serialization foundation, and target-specific provider lowerings for local,
AWS-local, AWS, and Kubernetes.

The program must preserve the substantial implementation already present while
removing duplicated security and serialization machinery before it becomes a
permanent cross-runtime contract.

### Program completion contract

v0.8 is complete only when all of the following are true at one exact candidate
commit. These outcomes are intentionally user- and system-observable; completing
an internal refactor without its vertical proof does not satisfy them.

1. **One authored graph:** the same application source produces deterministic,
   redacted plans for every advertised target, and unsupported semantics fail
   before mutation with a stable compatibility diagnostic.
2. **One integrity foundation:** every maintained canonical byte, digest,
   signature, cursor, and durable authority record is registered, versioned, and
   owned; the source gates find no unregistered private implementation.
3. **One admitted execution model:** HTTP, webhook, broker, workflow/task,
   schedule, actor/alarm, and agent execution enter through canonical admission,
   preserve causal identity, and perform operation-specific authorization.
4. **Callable dependencies stay framework-managed:** direct and extracted calls,
   local helpers, and clean external packages preserve provider requirements
   without exposing credentials, topology, target branches, or runtime imports.
5. **Time has explicit semantics:** portable schedules preserve definition,
   instance, occurrence, fencing, misfire, retry, pause, update, cancellation,
   history, and authority semantics; processor timers, actor alarms, and raw
   infrastructure cron remain deliberately distinct.
6. **Actors survive distributed reality:** calls, messages, connections, nested
   calls, alarms, cancellation, relocation, restart, rollout, and teardown retain
   one actor authority and durable ownership model.
7. **Targets preserve the graph's guarantees:** local, AWS-local, Kubernetes, and
   AWS receive only the maturity claim proven by their exact access, lifecycle,
   drift, observability, lakehouse, security, and cost evidence.
8. **The authored experience improves:** GuestBook remains the readable minimum,
   Chirp demonstrates distributed composition, and Agentic Start remains a
   polished product framework; none needs internal packages or new integrity,
   admission, scheduling, credential, or target ceremony.
9. **Upgrade and rollback are real:** every durable format has a reader/writer
   phase, interruption recovery, telemetry, rollback boundary, and removal
   condition, with previous-release evidence where the lifetime requires it.
10. **The release claim is reconstructible:** every accepted RFP requirement
    joins to a requirement class, work package, exact commit, evidence packet,
    command, artifact, environment, and cleanup receipt.

The candidate is not complete while a release-required item is externally
blocked. A claim-required item blocks its named claim. The maintainer may narrow
a claim, but the implementation agent may not silently redefine success to make
the scorecard green.

### Convergence seam contract

The four cleanup seams below are related but not interchangeable. This table is
the operational bridge between the source findings and the work packages: it
names the canonical owner, the semantics that remain local, the first bounded
cutover, and the evidence that permits the next cohort to begin.

| Seam | Canonical shared owner | Semantics that remain domain-owned | First bounded cutover | Proof before widening |
| --- | --- | --- | --- | --- |
| Canonical values | `@applik8s/core` Canonical JSON v1 algebra plus named policies; compiler/TypeKro boundary owns explicit reference adapters | Unsupported-value policy, reference meaning, persisted lifetime, digest purpose, and public diagnostics | Non-expiring application-graph and deployment-contract digests | Exact old/new byte vectors, cross-runtime parity, explicit adapter coverage, digest compatibility disposition, and removal or registration of the migrated private serializer |
| Signed envelopes | `@applik8s/runtime` portable sign/verify orchestration over core wire contracts | Typed payload, purpose, audience, lifetime, authorization, key namespace, retry/resume behavior, and public error mapping | Request-local command/query/stream tokens before durable cursors | Node/WebCrypto fixed vectors, tamper/expiry/cross-purpose negatives, domain differential tests, source-gate closure, and a registered legacy reader only where measured lifetime requires one |
| Admission | `@applik8s/core` validated context and narrowed views; verified ingress adapters construct it | Transport proof, operation authorization, idempotency/checkpoint authority, principal provenance, and execution-family lifecycle | Authenticated HTTP/browser plus request-local command/query/stream ingress | Exhaustive adapter-matrix row, provenance/substitution negatives, causal and authority parity, generated-worker proof, and no competing private principal/trusted-context shape |
| Scheduling | Canonical definition/instance/occurrence graph and provider-neutral occurrence admission | Workflow durability, processor lifecycle, actor alarms, raw infrastructure cron, provider precision, overlap, misfire, retry, cancellation, and history limits | `schedule(parameters, closure)` plus compatible static workflow cron and one-time execution | Executable `lower`/`preserve`/`reject` matrix, deterministic-time differential tests, occurrence/acknowledgement fault injection, provider lifecycle proof, and removal of the migrated parallel scheduler authority |

For every row, the first cutover is a review boundary, not permission for a
repository-wide rewrite. The next cohort starts only after the prior cohort's
source inventory, compatibility record, developer-experience fixture, and
acceptance packet agree at one commit. If behavior cannot be preserved exactly,
the plan records a deliberate domain policy or a stable rejection diagnostic; it
does not silently normalize the difference away.

Each cutover review must answer the following questions with executable evidence,
not architectural intent:

1. **Ownership:** Is there exactly one canonical implementation of the shared
   mechanism after the cutover, with an acyclic public dependency path?
2. **Semantic parity:** Do the migrated domain's accepted values, rejected values,
   public errors, authorization, retries, cancellation, and persisted bytes remain
   equivalent—or is every deliberate difference explicitly versioned?
3. **Retained-state safety:** Can the previous supported reader, the new reader,
   interruption recovery, and rollback consume every value they are contractually
   required to encounter?
4. **Deletion:** Was the superseded private implementation deleted, or is the
   exact bounded compatibility reader registered with telemetry, an owner, and a
   removal release?
5. **Developer experience:** Does the clean external fixture remain at least as
   concise and type-safe, without new serializers, signers, admission wrappers,
   provider-runtime imports, target branches, or scheduler ceremony?
6. **Operational truth:** Do failure diagnostics, observability, cleanup, and
   provider-specific evidence support the claimed maturity without treating
   telemetry or cached projections as a second authority?

A `yes` to only the ownership question is not consolidation. A migrated caller
that still leaves the old writer reachable, changes a domain contract implicitly,
or requires application glue remains an incomplete cutover even when its unit
tests pass.

### Concrete cleanup end states

The four convergence seams exist to remove specific, observed duplication. They
are not invitations to introduce a generic utility layer and declare the cleanup
complete. Each seam closes only at the following measurable end state:

| Observed pain | Required end state | Explicit non-goal | Merge blocker |
| --- | --- | --- | --- |
| HMAC, base64url, constant-time comparison, expiry, and token parsing are repeated in command, query, stream, task-query, object-storage, and search paths | One portable signed-envelope mechanism owns bytes, signing, verification, expiry, key selection, and purpose separation. Each execution family supplies only its typed payload, lifetime, authorization binding, and public error mapping. | A universal token payload or one error vocabulary for unrelated domains | Any maintained writer still contains private cryptographic mechanics, cross-purpose decoding succeeds, or retained values lack a registered reader/removal phase |
| Canonical-looking JSON exists in graph, deployment, compiler, client, and provider code with subtly different value rules | One Canonical JSON v1 algebra owns ordering and byte production. Every consumer names a domain policy, and TypeKro/CEL/runtime references cross only explicit adapters. | Pretending every domain accepts the same values or silently coercing unsupported objects | An unregistered serializer remains, two runtimes disagree on a fixed vector, or a reference/value policy is implicit |
| Principal, authority version, and trusted context are reconstructed independently at request and delivery boundaries | One validated admission context is constructed only after transport-specific evidence verification; each execution family consumes an immutable narrowed view and retains its own operation authorization and lifecycle authority. | Moving transport proof, domain authorization, checkpoints, or idempotency into a generic admission service | A maintained ingress defines a private authority shape, fabricates a human principal, loses causal identity, or accepts substituted provenance |
| Application schedules, workflow timers, delayed starts, processor convergence, actor alarms, and infrastructure cron overlap in vocabulary | The semantic matrix gives every surface an executable `lower`, `preserve`, or `reject` disposition. Only exactly compatible surfaces share definition/instance/occurrence machinery; workflow, processor, actor, and infrastructure ownership stays explicit. | Forcing all time-based behavior through one API or approximating unsupported provider semantics | A migrated surface changes cadence, precision, timezone, overlap, misfire, retry, cancellation, fencing, or history behavior without an explicit versioned contract |

For each row, the source inventory is both a starting count and a closure proof:
every named source ends as a canonical owner, canonical consumer, explicit domain
adapter, or time-bounded compatibility reader. `pending-migration` is not a
completed cleanup state. The acceptance packet records the exact deleted code or
the registry entry that makes retained compatibility finite.

Shared ownership must also preserve package shape. Portable byte and validation
contracts may move downward into focused core/runtime subpaths; domain payloads,
authorization, lifecycle, and provider behavior must not move downward merely to
reduce duplication. A cutover that creates a cyclic dependency, a broad umbrella
import, or a framework "god package" fails review even if it reduces line count.

The cleanup is measurably complete only when all named source-inventory paths
have a canonical-owner or bounded-compatibility disposition, migrated packages
contain no private copy of the shared mechanism, and the maintained authored
fixtures require no serializer, signer, admission wrapper, credential, target
branch, or scheduling adapter from application code.

## Current-state reconciliation

The v0.8 worktree is not a blank implementation. At the time this plan became
authoritative it contained a completed narrow typed HTTP-to-workflow slice and a
partially implemented callable-provider slice spanning HTTP, workflows, tasks,
schedules, actors, agents, provider packages, compiler discovery, and workload
placement. Preserve that work as reviewable checkpoints and characterize its
behavior before changing foundations underneath it.

The callable-provider implementation may continue to accumulate deterministic
coverage while Runtime Integrity is built, but it cannot advance beyond
`implemented` until the canonical admission adapters used by every affected
execution boundary are integrated. Rebase or adapt the slice onto the shared
foundation; do not discard it and do not recreate a parallel provider-runtime
path merely to satisfy phase ordering.

Before the first consolidation edit, record a baseline inventory containing:

- every current canonicalization, signing, verification, cursor, admission, and
  scheduling implementation and its public or persisted consumers;
- golden inputs, exact bytes, accepted legacy values, and current error behavior
  for every persisted or resumable format;
- generated artifacts and workload or credential placement for every callable
  execution family already implemented;
- package dependency direction and every application or provider import of an
  internal runtime module; and
- the exact deterministic commands that reproduce the baseline.

The inventory is characterization evidence, not an endorsement of duplicated
behavior. Unexpected differences become explicit domain-policy decisions or
fail-closed incompatibilities before a shared implementation replaces them.

## Non-negotiable principles

- Checkpoint unique work before rebasing, deduplicating, or changing history.
- Implement retained fixes in canonical source. Never port patched `dist` files.
- Keep the narrow v0.7.x HTTP-to-workflow unblock separate from the larger v0.8
  refactor.
- Canonical JSON bytes are defined before signatures and digests depend on them.
- Domain-specific cursor and token payloads remain distinct while sharing one
  signed-envelope substrate.
- Identity admission is normalized once; execution families consume narrowed
  views and retain their own operation authorization.
- Provider selection, credentials, readiness, topology, and private runtime
  dependencies remain framework-managed.
- Actor alarms remain actor timers. They are not application schedules.
- AWS-local proves API fidelity only. It never substitutes for real-AWS evidence.
- GuestBook, Chirp, and Agentic Start are the in-repository acceptance
  applications. Downstream products are dogfooding consumers, not release gates.
- v0.8 is an implementation-and-convergence release. Do not invent unrelated
  public capability while closing its accepted contracts. A new API is allowed
  only when an accepted RFP requires it or an acceptance application proves that
  the existing shape cannot express the required behavior.
- Compatibility is explicit rather than accidental. Every public or persisted
  contract change names its compatibility class, migration owner, rollback
  boundary, and removal release before implementation is considered complete.

### Priority order and deliberate non-unification

When several incomplete slices are independently actionable, use this order. It
is a dependency and risk order, not a license to skip the evidence states or to
serialize work that is genuinely independent:

1. **P0 — integrity and authority correctness:** Canonical JSON policies, signed
   envelopes, canonical admission, durable-format migration, causal identity,
   authorization, tenancy, secret isolation, and lifecycle ownership.
2. **P1 — one expressive execution model:** callable provider injection,
   function-native schedules where semantics are exactly portable, actor
   authority, deterministic graph planning, inferred runtime access, and the
   local development/runtime contract.
3. **P2 — breadth and maturity claims:** additional provider lowerings,
   observability and lakehouse backends, AWS/Kubernetes qualification,
   performance and cost history, acceptance-product polish, and release
   packaging.

A P2 provider implementation may be characterized while P0 is active, but it
must not introduce another signer, serializer, admission shape, credential path,
or scheduler authority. A P1 surface may reach `implemented` against the existing
foundation, but cannot become `integrated` until the P0 contract it consumes is
canonical. Security, data-loss, authority, and lifecycle regressions always
preempt this ordering.

The convergence target is one owner for shared mechanics, not one abstraction
for every domain. Specifically, v0.8 must **not**:

- merge command, query, stream, workflow, actor, search, object-storage, or
  schedule payload schemas merely because they use the same envelope bytes;
- erase domain-specific authorization, retry, cancellation, expiry, cursor,
  checkpoint, or public-error semantics behind a generic token API;
- force graph, deployment, manifest, and client-state serializers onto one
  normalization policy when their declared Canonical JSON adapters differ;
- turn processor timers, actor alarms, workflow durability, or raw
  infrastructure cron into application schedules when the semantic matrix does
  not prove equivalence; or
- move product-domain modules into framework packages solely to reduce generated
  application size or package count.

The desired result is fewer independent security-critical implementations and
fewer competing authorities, while retaining explicit typed domain contracts.
Source-inventory closure, differential behavior, and developer-experience
fixtures measure that result; raw file, line, or package counts do not.

### Scope boundary

This plan owns the reusable Applik8s contracts, packages, generated artifacts,
providers, and the three maintained acceptance applications. It does not own a
downstream product implementation, downstream product data migration, or
customer-specific acceptance criteria. Downstream validation receives a
provider-neutral handoff only after the applicable work package is `integrated`;
the handoff contains public APIs, compatibility guarantees, fixtures, commands,
and known limitations, but no downstream source or confidential product names.

Dogfooding may discover a framework defect. Such a defect enters this plan only
when it is reduced to a provider-neutral regression against a public contract.
Product-specific workflow or schema design remains in the downstream repository
and cannot silently enlarge the v0.8 release gate.

The cleanup is not complete merely because common code moved into a shared
package. It must also prove that:

- execution packages no longer contain private cryptographic envelope mechanics;
- every canonicalization domain names its Canonical JSON policy and any explicit
  reference adapter instead of depending on a lookalike serializer;
- ingress packages construct one validated admission context and consume only
  their narrowed domain view; and
- scheduling shares definition, instance, occurrence, lease, and provider
  projection machinery only where semantics are identical. Workflow durability,
  processor checkpoints, actor alarms, and raw infrastructure cron remain owned
  by their existing domains.

The downstream validation handoff is produced only after these framework-owned
invariants reach `integrated`. It validates public contracts from a clean
consumer; it is not a place to finish framework internals or compensate for a
missing in-repository gate.

## Program control and evidence states

Every ledger row and implementation slice uses one of these evidence states. The
machine-readable acceptance manifest retains its conservative `implemented`
boolean: it stays `false` until the gate's required integrated and live evidence
has passed.

- `not-started`: no canonical implementation exists;
- `characterized`: the current behavior and failing regression are recorded;
- `implemented`: canonical source and deterministic tests pass;
- `integrated`: all affected packages, generators, and maintained providers pass;
- `live-qualified`: the exact required environment passed with verified cleanup;
- `externally-blocked`: implementation is complete but named external evidence is
  unavailable; or
- `rejected`: the proposed behavior was deliberately excluded with rationale and
  regression protection.

`implemented` never implies `live-qualified`. Documentation and scorecard flags
must use the weakest truthful state. Each transition records the exact commit,
command, environment, evidence artifact, and cleanup result.

### Release requirement classes

Evidence state and release necessity are separate dimensions. Every acceptance,
scorecard, target-compatibility, and reconciliation row carries one of these
requirement classes so that a difficult live gate cannot be silently treated as
optional and a preview claim cannot unnecessarily block unrelated work:

- `release-required`: part of the accepted v0.8 stable contract. The release
  candidate cannot pass while this row is incomplete or externally blocked.
- `claim-required`: required only for the named target, provider, or maturity
  claim. Missing evidence blocks that claim. Removing or downgrading the claim
  requires a maintainer decision and coordinated changes to the RFP, scorecard,
  acceptance manifest, target matrix, and documentation.
- `non-gating`: characterization, downstream dogfooding, or optional evidence
  that improves confidence but is not part of the public v0.8 contract. A row may
  use this class only when no accepted RFP or advertised compatibility claim
  requires it.

`externally-blocked` never changes a row's requirement class. It records why the
evidence cannot currently be obtained; it does not waive the evidence. The
machine-readable manifests are authoritative for the assigned class, and the
consistency gate rejects a prose/manifests mismatch.

### Decision authority and change control

Implementation choices that preserve an accepted contract—module boundaries,
private helper names, test organization, and equivalent internal algorithms—do
not require routine maintainer confirmation. Continue autonomously and record
the choice in the affected acceptance packet when it materially affects review.

The following decisions require an explicit maintainer disposition before the
implementation may proceed across that boundary:

- narrowing or removing an accepted stable capability or target claim;
- weakening an authority, security, tenancy, durability, lifecycle, or cleanup
  invariant;
- adopting a destructive or non-rollback-safe persisted-format migration;
- adding a new public execution concept when an accepted v0.8 concept can express
  the behavior; or
- publishing, tagging, releasing, or mutating a production environment.

Record such a decision with a stable identifier, affected contracts, considered
options, selected disposition, owner, commit, compatibility consequence, and any
follow-up removal release. A missing decision pauses only dependent work. It does
not justify inventing a compatibility shim or blocking independent lanes.

### Start and resume protocol

At the beginning of every implementation session:

1. read this plan, the concise `docs/v0.8-goal.md`, current goal objective,
   reconciliation ledger,
   source inventories, format registry, admission matrix, scorecard, acceptance
   manifest, and target matrix relevant to the active slice;
2. inspect the branch, worktree, recent commits, active test processes, and dirty
   files without discarding or rewriting work;
3. identify the single bounded slice already in cutover and finish, checkpoint,
   or truthfully block it before starting another writer, migration, or execution
   family;
4. rerun the smallest deterministic regression that proves the current failure,
   then expand to package, clean-consumer, generated-artifact, and live gates in
   proportion to the change; and
5. update the evidence packet and machine-readable state before claiming a state
   transition.

Diagnostic edits discovered during a failing gate remain part of the active
slice until they are either converted into a reviewed regression/fix or reverted
deliberately. Do not abandon them as unexplained worktree residue, and do not let
them silently broaden the slice.

## Definition of done for every implementation slice

A slice is complete only when all applicable items are satisfied:

1. The canonical source owner contains the implementation; generated output and
   patched `dist` files are never the source of truth.
2. Public types, runtime behavior, compiler lowering, generated source, package
   exports, and dependency manifests agree.
3. Positive, negative, adversarial, migration, and cleanup regressions exist in
   proportion to the risk.
4. Focused tests, affected package typechecks, formatting, and diff checks pass;
   broad gates run at the integration boundary rather than after every edit.
5. Clean packed-consumer evidence proves that undeclared workspace hoisting does
   not mask dependency or export defects.
6. Documentation shows the intended golden path and removes or labels obsolete
   syntax.
7. Persisted-format or authority changes include mixed-version, rollback, and
   failure-interruption evidence.
8. Live tests perform bounded preflight and leak-free lifecycle cleanup when a
   live environment is part of the maturity claim.
9. The reconciliation ledger and machine-readable scorecard are updated with no
   stronger claim than the evidence supports.

Each reviewable slice leaves a compact checked-in evidence record, either in the
reconciliation ledger or in a linked artifact, with:

- the contract or finding being closed and its canonical source owner;
- public and persisted compatibility classification;
- affected readers, writers, generators, providers, and targets;
- exact focused and integration commands with their results;
- migration phase, rollback boundary, telemetry, and removal condition when
  compatibility code remains;
- live environment, preflight result, resource ownership, and verified cleanup
  when live evidence applies; and
- remaining limitations or external blockers.

The record is part of the implementation. A diff with passing tests but without
enough evidence to reconstruct why its claim is valid remains `implemented` at
most and cannot silently advance an integrated or live-qualified gate.

### Developer-experience preservation gate

Foundation consolidation is successful only when it reduces internal duplication
without exporting that complexity to application authors. Every slice that changes
a public contract, generated application, compiler discovery, provider injection,
or target lowering must include a before/after golden-path fixture proving that:

- an application does not gain a new serializer, signer, admission wrapper,
  provider-runtime import, scheduling adapter, credential parameter, or target
  branch merely because the framework internals were consolidated;
- direct callable handles, extracted bound operations, module-local helpers, and
  clean external packages retain the same type inference and runtime behavior;
- target selection and provider qualification remain declarative and do not leak
  TypeKro, Alchemy, AWS, Kubernetes, or runtime implementation details into domain
  code;
- generated source remains reproducible, readable at its intended extension
  points, and free of undocumented internal imports; and
- any necessary public API change is smaller and more expressive than the syntax
  it replaces, with one documented migration and no parallel golden paths.

An implementation that centralizes machinery but adds application ceremony does
not pass its work package. When the framework cannot preserve the authored
surface, fail with an actionable compatibility diagnostic rather than requiring
users to reconstruct the internal boundary manually.

## Program risks and stop rules

The following risks receive explicit fail-closed controls. They are not deferred
to a final release review.

| Risk | Earliest detection | Required control | Stop rule |
| --- | --- | --- | --- |
| Cross-runtime canonical-byte drift | Canonical JSON and envelope fixed vectors | One versioned algebra, named domain policies, Node/WebCrypto/WASM/browser differential vectors | Do not migrate a signature, digest, cursor, or persisted identity until every maintained runtime agrees byte-for-byte. |
| Mixed-version state becomes unreadable | Format registry and upgrade fixtures | Release-A/B/C readers and writers, interruption recovery, rollback fixture, removal telemetry | Do not remove a legacy reader or advance its writer phase without proving the previous supported release can recover all rollback-window state. |
| Admission loses or fabricates authority | Admission adapter matrix and source inventory | One canonical validator, ingress-specific evidence verification, exact principal/operation parity regressions | Do not mark an ingress implemented while it defines a private admission shape, invents a human principal, or lacks negative authority tests. |
| Provider dependency metadata disappears through indirection | Callable-provider compiler fixtures | Recursive module/helper discovery, portable metadata, every execution-family lowering, credential-boundary assertions | Do not accept a provider handle that works only through a direct top-level call or relies on workspace hoisting/internal runtime imports. |
| Scheduling convergence changes semantics | Scheduling semantic matrix and provider differential suite | Explicit mapping for occurrence identity, authority, overlap, misfire, retry, cancellation, and history | Do not lower an existing scheduling surface through the shared graph until every applicable semantic cell is preserved or rejected with a diagnostic. |
| Live evidence mutates or leaks shared infrastructure | Bounded environment preflight and teardown verification | Ownership proof, TypeKro/Alchemy lifecycle teardown, UID-safe cleanup, absence verification | Abort before mutation when ownership or capacity is ambiguous; a leaked lifecycle fails the live gate. |
| Scope growth obscures convergence | RFP/scorecard traceability review | Every public API change cites an accepted RFP or acceptance failure and records compatibility/removal | Reject unrelated capability work from v0.8 even when locally useful. |
| Performance evidence is noisy or misleading | Repeated baseline gate | Fixed fixtures, warmup, multiple samples, robust statistics, stored history | Do not claim improvement or regression from one timing sample, and do not waive an unexplained budget breach. |

A stop rule pauses only the affected dependency lane unless continuing another
lane would duplicate or invalidate the unfinished foundation. External provider
unavailability is recorded as `externally-blocked`; it never converts a missing
live qualification into a passing claim.

## Dependency lanes

The program is a dependency graph, not one serial queue:

```text
checkpoint + reconciliation
  -> release-line HTTP/workflow fix
  -> v0.8 rebase
      -> Canonical JSON v1
          -> signed envelopes
              -> canonical admission
                  -> callable provider injection
                  -> scheduling convergence
                  -> actor authority completion

after canonical admission:
  provider injection ----> target/provider parity ----> product acceptance
  scheduling ------------> local/Kubernetes/AWS evidence ------^
  actors ----------------> distributed lifecycle evidence ------^
  runtime integrity -----> migration/security/performance ------^
```

Work in separate lanes may proceed concurrently only when it does not duplicate
an unfinished foundation. Canonical JSON precedes signatures; signed envelopes
precede admission token migration; canonical admission precedes new ingress
lowerings. Product applications may characterize gaps throughout, but their
release evidence is rerun only after the affected foundations integrate.

## Consolidation ownership map

Convergence means removing duplicated mechanism without erasing domain semantics.
The following ownership map is normative for the cleanup. A shared foundation
owns bytes, validation, and transport-safe mechanics; the consuming domain keeps
its payload, authorization, lifecycle, and public API.

| Current duplication | Canonical owner | Domain-owned remainder | Completion evidence |
| --- | --- | --- | --- |
| HMAC, base64url, constant-time verification, expiry, and signed token parsing in command, query, stream, task-query, object-storage, and provider search runtimes | Portable Runtime Integrity signing/verification package over canonical bytes | Purpose-specific payload schemas, lifetimes, key namespaces, authorization, and public error mapping | Shared fixed vectors; cross-purpose rejection; source inventory finds no private implementation; mixed-version readers pass |
| Search cursor codecs in deterministic, PostgreSQL, and OpenSearch providers | Search package cursor contract using the shared envelope substrate | Provider-specific continuation state and query semantics | One provider-differential suite consumes one codec and proves incompatible provider state fails closed |
| Canonical-looking JSON implementations in application graph, deployment contract, compiler manifest, and client store | Core Canonical JSON v1 algebra | Named domain policies and explicit TypeKro/CEL/reference adapters | Byte-for-byte Node, browser, WASM, worker, and compiler vectors plus digest migration fixtures |
| Principal, authority revision, and trusted-context validation in request identity, Kubernetes server, reactive, query, and stream gateways | Core canonical admission context and validator | Transport evidence verification at each ingress and operation authorization in each execution family | Exhaustive admission adapter matrix, negative provenance tests, and a source gate rejecting private admission shapes |
| Application schedules, workflow cron, one-time workflow execution, dynamic reconciliation, processor convergence, actor alarms, and raw Kubernetes cron resources | Shared schedule definition/instance/occurrence graph only where the portable semantic matrix is preserved | Workflow execution, processor lifecycle, actor authority, and infrastructure escape-hatch semantics remain with their domains | Source-surface disposition table and provider differential tests; unsupported convergence produces compile-time diagnostics |

Package ownership must remain acyclic: core owns synchronous portable data
contracts and validation; runtime-level packages own asynchronous cryptographic
adapters; execution-family packages own typed payloads and authorization;
compiler packages lower portable metadata; provider packages contribute only
provider behavior. A consolidation is incomplete if application or provider code
must import an internal runtime implementation to use the public contract.

## Semantic authority map

Convergence must not create a second source of truth merely because several
providers need the same behavior. Every portable capability names its canonical
authority, the state that may be reconstructed from it, and the state that is
evidence only. Provider lowerings may cache or project this state, but they may
not silently become competing authorities.

| Capability | Canonical authority | Rebuildable or derived state | Evidence only |
| --- | --- | --- | --- |
| Application topology and dependency provenance | Versioned semantic application graph plus its canonical graph digest | Target plans, manifests, workload placement, inferred dependency edges, and redacted visualizations | Compiler logs and plan-render timing |
| Admission and execution identity | Validated canonical admission context plus the operation's authorization receipt | Narrowed HTTP, workflow, schedule, actor, processor, query, and agent views | Transport headers, broker attributes, and trace baggage after verification |
| Durable workflows and tasks | Selected workflow provider's durable history, addressed through provider-neutral run and task identities | UI projections, resource-status summaries, and bounded subscription indexes | Push notifications and polling caches |
| Application schedules | Shared definition and instance desired state plus the durable occurrence/lease record | Provider-native schedules, delivery targets, history views, and retry projections | EventBridge, CronJob, or broker delivery metadata that has not been admitted |
| Actors and alarms | Actor state/journal and actor-owned alarm record under canonical actor authority | Placement, connection indexes, realtime subscriptions, and operational views | Pod identity, process-local mailboxes, and transient transport acknowledgements |
| Deployment and lifecycle | Semantic desired graph plus the Alchemy/TypeKro ownership record; the target API is authoritative for observed live state | Diffs, readiness summaries, drift reports, and generated plans | CLI output and controller events without a corresponding observed-state read |
| Runtime access | Inferred semantic requirements intersected with the selected target/provider guarantee contract | IAM, RBAC, network policy, secret projection, and workload credentials | Provider defaults and manually granted ambient privilege |
| Observability | Domain/runtime authorities above; telemetry is append-only diagnostic evidence | Logs, traces, metrics, exemplars, and operational dashboards | Telemetry must never be consulted as the only correctness or ownership record |
| Lakehouse publication | Immutable object plus committed publication manifest/receipt in the application transaction boundary | Catalog entries, partitions, query indexes, compaction plans, and analytics projections | Query-engine caches and incomplete uploads |
| Local development control | The same portable contracts as deployed targets; the supervisor registry owns only local process lifecycle | Hot-reload state, local endpoints, fixture status, and developer diagnostics | Process memory and terminal output after supervisor restart |

When a provider cannot preserve the named authority boundary, compilation or
deployment fails with a provider-compatibility diagnostic. A test that proves two
providers return the same value is insufficient if they arrived there through
different ownership, retry, or recovery semantics.

## Measurable convergence invariants

The cleanup is complete only when the source tree and generated artifacts prove
the following invariants. These are semantic budgets, not line-count targets:

1. **One canonical-byte algebra.** Every maintained digest, signature, cursor,
   deployment identity, and persisted receipt uses Canonical JSON v1 through a
   named domain policy. Alternate normalization is either an explicit adapter or
   rejected by the source inventory.
2. **One signed-envelope substrate.** Maintained packages contain no private HMAC,
   base64url, constant-time comparison, expiry, or key-rotation implementation.
   Purpose-specific payload codecs remain independently typed and cannot verify
   one another's envelopes.
3. **One admission context.** Every maintained ingress is present in the admission
   adapter matrix, constructs or validates the canonical context, and hands an
   execution-family-specific narrowed view to application code. No adapter
   invents a human principal, trusts client-authored identity, or substitutes a
   configuring principal for later execution.
4. **One dependency metadata path.** Direct calls, extracted bound methods,
   module-local helpers, and clean external packages preserve the same callable
   provider requirement through every maintained execution family.
5. **One portable schedule graph, bounded by semantics.** Compatible schedule
   definitions, instances, and occurrences share the graph. Processor lifecycle,
   actor alarms, and infrastructure cron retain their distinct authority and
   lifecycle semantics.
6. **No hidden package privilege.** Generated applications and third-party
   provider packages use public exports, declare every dependency, and pass from
   a packed clean consumer without workspace hoisting or internal imports.
7. **No unowned compatibility code.** Every legacy reader, adapter, alias, and
   migration branch has telemetry, an owner, a rollback window, and a recorded
   removal release in the format registry or reconciliation ledger.

The source-inventory gates report the concrete remaining violations for these
invariants. They must not be implemented as brittle filename counts: an allowed
adapter is identified by its registered role, while a newly introduced private
implementation fails even if it replaces an older file one-for-one.

The executable registry for this claim is
[`v0.8-runtime-integrity-source-inventory.json`](v0.8-runtime-integrity-source-inventory.json).
Every named released-source finding has a stable identity, canonical owner,
disposition, evidence path, and remaining-work statement. The Runtime Integrity
gate must reject a missing known path, duplicate identity, unknown disposition,
closed row without evidence, or compatibility row that is absent from the format
registry. A broad source scan supplements this registry; it cannot replace it.

### Consolidation cutover proof

Shared machinery is justified by a completed semantic cutover, not by resemblance
between source files. Before introducing or widening a shared serializer, signer,
admission constructor, scheduling primitive, or provider-runtime seam, the slice
must record:

1. the exact existing producers, consumers, persisted values, public errors, and
   authored golden-path fixture;
2. fixed behavior vectors that characterize the old implementation before its
   replacement is used;
3. the one consumer cohort being migrated, including positive, negative,
   adversarial, mixed-version, and interruption cases appropriate to its lifetime;
4. the canonical owner and the domain-owned semantics that deliberately remain
   outside that owner;
5. a source or import gate that fails if the migrated private mechanism returns;
6. the old code removed in the same slice, or an explicit compatibility-reader
   entry with owner, telemetry, rollback window, and removal release; and
7. a clean packed-consumer fixture proving the public developer experience is no
   more complex and requires no new framework-internal imports or configuration.

A proposed abstraction that cannot name its first migrated cohort and the code it
deletes or places under a bounded compatibility record is characterization, not
implementation. It must not become a new public package or golden path. A shared
foundation also does not earn completion merely because all callers use it: the
domain differential, source-inventory row, format-registry disposition, and
acceptance packet must agree at the same qualifying commit.

This rule applies equally to Runtime Integrity and scheduling convergence. The
scheduling matrix must reject a missing maintained source/provider cell and must
record `lower`, `preserve`, or `reject` with the semantic reason; a shared helper
does not imply that processor timers, workflow durability, actor alarms, and
infrastructure cron have acquired the same authority.

## Reviewable work packages

The phases below define dependency order; these work packages define the review
and commit seams. A package advances independently when its prerequisites and
exit evidence pass. Do not combine several packages merely because they touch the
same compiler file.

### Planning metadata and slice sizing

The work-package table deliberately describes outcomes rather than calendar
promises. Before a package becomes the active cutover, its evidence packet or
temporary reconciliation-ledger row must also name:

- one `implementationOwner` responsible for closing the bounded slice;
- one `reviewOwner` responsible for independently checking the contract and
  evidence, which may be the maintainer when no separate reviewer is assigned;
- `size` as `S`, `M`, or `L`, based on the expected review surface rather than
  elapsed time;
- `uncertainty` as `low`, `medium`, or `high`, with the unresolved semantic,
  provider, migration, or environment question named explicitly;
- the exact `nextCommand` that can advance or falsify the slice; and
- any external prerequisite or maintainer decision that blocks only that lane.

An `S` slice should normally affect one canonical owner and one consumer family.
An `M` slice may include a canonical owner plus its generated/runtime integration.
An `L` slice is a work package, not a commit: split it into independently
reviewable findings before implementation. A proposed change that spans multiple
shared writers, persisted-format phases, or execution families is oversized even
when its diff is small.

These fields are planning controls, not performance metrics. Do not invent
calendar estimates before the relevant characterization gate establishes the
work. Re-estimate after a newly discovered compatibility or live-provider
constraint, record the reason, and keep the current execution cursor pointed at
one falsifiable next step.

Large compiler or generator changes use characterization-first commits: record
the emitted source/manifest behavior, add a failing semantic regression, then
change the lowering. This keeps a generated-code diff reviewable and separates a
public-contract decision from mechanical regeneration.

### Execution cadence and work-in-progress limits

At most one migration slice per shared foundation (`RI-1`, `RI-2`, or `RI-3`) is
in cutover at a time. A second lane may characterize behavior or add independent
provider evidence, but it may not introduce another writer, compatibility shim,
or admission shape before the active migration slice closes its source-inventory
row. This keeps partial migrations reviewable and rollback-safe.

Each implementation cycle is deliberately small:

1. select one ledger finding and one canonical owner;
2. capture the old behavior and the failing semantic regression;
3. implement the canonical primitive or migrate one consumer family;
4. run focused, package, clean-consumer, and generated-artifact gates applicable
   to that slice;
5. update its format/admission/scheduling registry rows and acceptance packet;
6. commit the slice before starting the next writer or execution family; and
7. run the broader milestone audit only when the slice changes an integrated
   boundary or completes a work package.

Do not leave a compatibility reader, old writer, or generated-source fallback
unrecorded between cycles. If a slice cannot close because of an external live
environment, checkpoint the deterministic implementation as
`externally-blocked`, record the exact missing evidence, and continue only on an
independent lane.

### Scope burn-down and release-triage checkpoints

This plan is intentionally comprehensive, but comprehensiveness must not turn
v0.8 into an unbounded convergence project. At the end of every milestone, and
before opening any `L` slice, produce a compact burn-down containing:

- every incomplete `release-required` row and the shortest remaining path to its
  evidence;
- every incomplete `claim-required` row grouped by the public claim it blocks;
- every `non-gating` row that is being deferred, with confirmation that no
  accepted RFP or advertised compatibility statement depends on it;
- the remaining high-uncertainty decisions or external environments; and
- the smallest independently reviewable slice that advances the critical path.

The burn-down is a scope-control instrument, not permission to redefine the
release. The implementation task may defer a genuinely non-gating improvement,
but only the maintainer may narrow an accepted claim or reclassify a release
requirement. A newly discovered improvement does not block v0.8 unless it closes
an accepted requirement, a security/authority/durability/lifecycle invariant, a
maintained acceptance failure, or a release-shape defect. Cosmetic perfection,
downstream-product convenience, and speculative future capability remain outside
the blocking path.

Every burn-down must distinguish:

- **mechanism remaining:** a canonical owner or compiler/runtime seam is absent;
- **migration remaining:** the owner exists but maintained consumers, retained
  formats, or compatibility readers have not completed their recorded phase;
- **qualification remaining:** deterministic semantics are integrated but a live
  provider, lifecycle, performance, cost, or cleanup claim lacks exact evidence;
- **product remaining:** a maintained acceptance application exposes a framework
  defect or developer-experience regression; and
- **downstream-only validation:** a consumer-specific journey may discover a
  generic defect but is not source, scope, or release authority for Applik8s.

This prevents a broad completion percentage from hiding whether the remaining
work is architectural, migratory, evidentiary, or product-facing. Select the next
slice from the earliest blocking category on the dependency path, not from the
easiest count to make green.

If the estimated review surface of the remaining release-required work expands
materially at a checkpoint, split it by canonical owner and consumer family,
record the cause, and continue with the smallest prerequisite. Do not hide the
expansion in a larger diff and do not lower the evidence standard to preserve a
calendar expectation.

### Required acceptance packet per work package

Each work package writes or updates one stable, checked-in acceptance packet. The
packet is intentionally small and links to larger generated artifacts rather than
copying them into prose.

Packets live at `docs/evidence/v0.8/<work-package>.json` and use one shared schema.
Every packet contains at least:

- `workPackage`, `state`, `implementationCommit`, and `qualifiedCommit`;
- `implementationOwner`, `reviewOwner`, `size`, `uncertainty`, and the exact
  `nextCommand` used to resume or falsify unfinished work;
- exact `commands` with exit status and an explicit deterministic/live class;
- content-addressed `artifacts` and the contract each artifact proves;
- `compatibility` with reader/writer phase, rollback boundary, telemetry, owner,
  and removal release where applicable;
- `environments` with preflight and cleanup results, without secrets or mutable
  credentials;
- `developerExperience` with the before/after golden-path fixture and any public
  migration; and
- `limitations` and `externalBlockers` that prevent stronger claims.

The packet schema and validator are themselves release artifacts. The scorecard
gate must reject a work-package claim when its packet is absent, stale relative to
the qualified commit, references a missing command/artifact, or claims live
qualification without a successful cleanup receipt. Until the shared validator
lands, the reconciliation ledger is the authoritative temporary packet and must
carry the same fields.

### Requirement-to-evidence join

Before `M5`, the scorecard validator must join each accepted claim through one
unbroken chain:

```text
RFP requirement
  -> scorecard pillar
  -> acceptance gate and requirement class
  -> work package
  -> exact qualifying commit
  -> checked-in evidence packet
  -> command/artifact/environment/cleanup receipt
```

The join uses stable identifiers rather than prose matching. It fails for orphan
requirements, gates without a requirement class, packets that qualify an older
contract commit, target claims without the target-specific environment receipt,
and evidence artifacts that are missing or not content-addressed. A passing test
that cannot be joined to the requirement it proves is useful diagnostic evidence
but does not advance the release state.

The machine-readable manifests do not acquire optimistic requirement classes by
inference. Their initial classification is an explicit plan slice: compare each
accepted RFP and advertised target, assign `release-required`, `claim-required`,
or `non-gating`, and request a maintainer decision wherever the classification
would narrow an accepted claim. Until that classification and validator land,
the prose contract remains authoritative and no omitted field is treated as
optional.

### Provider-neutral downstream validation handoff

Downstream dogfooding is deliberately outside the release repository, but the
framework must make it reproducible. After a work package reaches `integrated`,
its handoff consists of:

- the exact coordinated package version or source commit;
- public APIs and golden-path fixtures only, with no internal runtime imports;
- compatibility and persisted-format expectations;
- deterministic commands a clean external package can run;
- target prerequisites and truthful unsupported-provider diagnostics;
- known limitations and the exact evidence state; and
- a defect-report template that reduces downstream failures to a public,
  provider-neutral regression.

The downstream repository owns its schemas, migrations, product workflows, and
acceptance journeys. Its results may strengthen confidence or discover a generic
framework defect, but they neither replace the maintained acceptance applications
nor silently add a release requirement.

### Progressive cutover discipline

Runtime Integrity migrations are progressive, not flag-day rewrites:

1. Characterize the current writer and every supported reader.
2. Land the canonical implementation behind an internal compatibility adapter
   while retaining the current public API.
3. Migrate one domain writer and its readers together, with old/new differential
   tests and interruption recovery.
4. Make the source inventory reject new private implementations before migrating
   the next domain.
5. Advance the default writer only when rollback-window readers can consume its
   output.
6. Remove a compatibility reader only at its format-registry removal release and
   only after retained-state or lifetime evidence proves it is no longer needed.

Provider injection follows the same rule at execution-family boundaries: first
characterize emitted dependency metadata and workload placement, then switch that
family to the shared callable-provider path, then prove a packed external package
and exact credential isolation before moving to the next family.

## Milestone control and release claims

Work-package completion is the unit of implementation review. Milestones are the
points where several packages become one usable framework capability. A milestone
advances only when every blocking work package has reached the stated evidence
level; progress in a parallel lane does not compensate for a missing prerequisite.

| `M4 target parity` | `GP-1`, `RA-1`, `LR-1`, `OB-1`, `LH-1`, `TP-1`, `DX-1`, plus each provider required by a target's compatibility row | `integrated`; `live-qualified` for stable target claims while contract-only rows remain explicitly preview/unsupported | Product qualification on already qualified targets; migration/performance qualification against frozen fixtures | Exact target plans, lifecycle/security/drift receipts, local/development journeys, observability/lakehouse packets, and truthful cost evidence |

independent work to continue and permits a review packet to be assembled, but it
does not authorize a stable compatibility claim whose required environment was
not exercised. Before release review, each externally blocked row must have one
of three explicit dispositions:

1. obtain the required evidence and advance it;
2. narrow the public compatibility/maturity claim, with the scorecard, target
   matrix, documentation, and diagnostics changed together; or
3. keep the release candidate blocked.

The implementation agent may not silently choose disposition 2 for an accepted
stable requirement. Narrowing an accepted release claim is a maintainer decision.
Missing credentials, account access, provider availability, or cluster capacity
must name the exact blocked command and prerequisite; they are not generic
waivers.

At each milestone, run a consistency audit that proves:

- the execution plan, RFPs, scorecard, acceptance manifest, target matrix, format
  registry, admission matrix, and reconciliation ledger describe the same state;
- every `implemented: true` flag points to a real command and evidence artifact;
- every public example uses the current golden path and no removed compatibility
  syntax;
- every remaining compatibility branch has an owner and removal condition; and
- the next milestone starts from one exact commit with a clean or explicitly
  inventoried worktree.

Milestone audits are not invitations to pause for routine confirmation. Continue
through the accepted plan unless the audit exposes a real authority decision,
destructive external action outside the authorized test scope, or a stop-rule
violation.

For a source path that no longer exists on the active branch, record the commit

The first Runtime Integrity review sequence is fixed so the program does not
begin with a cross-repository rewrite:

1. characterize and register the four existing canonical-JSON domains without
   changing their bytes;
2. land Canonical JSON v1, its named policies, and fixed vectors as `RI-1`;
3. migrate one digest domain at a time, starting with non-expiring build-time
   artifacts before resumable or durable records;
4. land the signed-envelope substrate and migrate one gateway family at a time;
5. consolidate the three search providers behind the shared search cursor codec;
6. land canonical admission validation and migrate one ingress family at a time;
   and
7. only then advance callable-provider, scheduling, or actor slices that require
   the new admission contract from `implemented` to `integrated`.

1–6, but they must not create a private admission token or alternate canonical

### Runtime Integrity cohort order

The foundation is migrated by consumer cohort, not by sweeping package rewrite.
Each row is an independently reversible cutover whose commit changes one
canonical owner and the named readers/writers together. A later cohort cannot
silently repair or reinterpret an earlier cohort's bytes.

| Order | Cohort | Required cutover proof |
| --- | --- | --- |
| `RI-1a` | Application graph and deployment-contract digests | Characterize existing bytes, adopt one named Canonical JSON policy, prove old/new digest disposition, reject unsupported values, and register any retained artifact reader. |
| `RI-1b` | Compiler manifests and client-store snapshots | Cross-runtime fixed vectors include reference adapters; generated artifacts are deterministic; a browser/worker consumer reads the exact canonical bytes without importing compiler or TypeKro internals. |
| `RI-2a` | Request-local command/query/stream envelopes | One shared purpose-separated envelope substrate; tamper, purpose substitution, expiry, size, and error-mapping differentials; no legacy reader unless lifetime evidence requires one. |
| `RI-2b` | Resumable task-query, object-intent, and search cursors | Maximum lifetime, key namespace, dual-read window, telemetry, and rollback are explicit; deterministic, PostgreSQL, and OpenSearch search providers consume one typed search codec. |
| `RI-2c` | Durable actor, schedule, lakehouse, and provider records | Fault injection at every committed writer boundary, mixed-version readers, interruption recovery, and a recorded decoder-removal release. |
| `RI-3a` | Authenticated HTTP, browser/SSE, command, query, and stream admission | Each transport verifies its own evidence, then constructs the canonical context; narrowed execution views preserve exact authorization and trusted-context behavior. |
| `RI-3b` | Workflow/task, broker, webhook, and provider callback admission | Redelivery and lost-response recovery preserve one operation identity and causal lineage; no adapter fabricates a human principal from payload fields. |
| `RI-3c` | Schedule, actor/alarm, agent, AI, and framework-service admission | Persisted authority remains bounded and future-safe; configuring principals are not replayed as execution principals; generated workers prove exact operation and credential placement. |

Every cohort closes only when its source-inventory row, format-registry phase,
focused differential tests, clean public export, compatibility disposition, and
rollback/removal record agree. The aggregate Runtime Integrity gate is a final
consistency check; it does not substitute for these cohort receipts.

### 3A. Canonical JSON v1

Define one platform-neutral and explicitly versioned canonical JSON algebra.
Named domain policies must cover:

- deterministic object-key ordering;
- `undefined` in objects and arrays;
- root `null`;
- finite numbers and negative zero;
- cycles and repeated references;
- unsupported runtime values;
- strings and byte representations; and
- TypeKro/CEL references through explicit adapters.

Migrate graph, deployment, compiler, client, workflow, schedule, actor, search,
and lakehouse digests onto named policies over this algebra. Fail closed when a
domain cannot be represented rather than silently choosing another policy.

### 3B. Versioned signed envelopes

Create one portable signed-envelope contract with:

- explicit purpose/audience separation;
- format version and algorithm;
- key identity;
- issuance and expiry;
- typed payload validation;
- encoded-size bounds;
- constant-time verification;
- Node and WebCrypto adapters;
- structured errors; and
- key-rotation support.

Commands, queries, subscriptions, tasks, object storage, search, celld tickets,
and lakehouse cursors keep distinct payload schemas. They share canonical bytes,
base64url handling, signing, verification, expiry, and error behavior.

Give deterministic, PostgreSQL, and OpenSearch providers one shared search cursor
codec. Providers contribute only provider-specific continuation state.

### 3C. Canonical admission context

Define one framework-produced and validated admission context containing:

- authenticated principal;
- authority revision;
- trusted-context values and digest;
- authorization receipt where required;
- operation and transport identity;
- correlation and causation;
- deadline and cancellation; and
- trace context.

The request identity boundary constructs and validates it once. HTTP, commands,
queries, subscriptions, processors, workflows, schedules, actors, agents, and AI
consume narrowed views. Their application authorization remains independent.

Admission construction must cover every maintained ingress explicitly:

- authenticated HTTP and browser/SSE requests;
- verified webhooks and provider callbacks;
- broker deliveries;
- workflow and task deliveries;
- schedule occurrences using a bounded scheduler service principal;
- actor calls and persisted alarm authority; and
- named framework service principals.

Each adapter verifies transport-specific evidence and produces the canonical
context. None may fabricate a human identity, reuse the principal that configured
a later schedule, or define another principal/trusted-context structure.

Maintain `docs/v0.8-admission-adapter-matrix.json` as the executable inventory for
this convergence. Every row names the evidence verifier, principal source,
operation-identity rule, transport, implementation state, regression command, and
remaining work. The parity gate enumerates this file and fails when a maintained
ingress is absent, when an implemented row lacks a regression, or when source
inventory finds a private principal/authority/trusted-context admission shape.
Adding an ingress therefore requires adding its canonical adapter and matrix row
in the same slice; prose-only coverage is not sufficient.

### 3D. Migration and evidence

- New versions emit only canonical v1 formats.
- Add an explicit bounded legacy decoder only where a durable released token can
  legitimately outlive deployment; never silently try multiple purposes.
- Add shared fixed vectors across Node, browser, WASM, worker, compiler, and
  provider runtimes.
- Prove cross-purpose substitution, tampering, expiry, truncation, wrong keys,
  oversized payloads, malformed canonical input, and ambiguous adapters fail
  closed.
- Add a source-level gate that prevents maintained gateways and providers from
  reintroducing private HMAC/base64url implementations or parallel admission
  context shapes.

Classify every persisted token or record as request-local, resumable/expiring, or
durable. Durable rolling migrations use read-legacy-and-v1/write-legacy,
read-legacy-and-v1/write-v1, then read-v1-only releases unless an exact migration
record proves that mixed readers and writers cannot coexist. A legacy decoder has
an owner, maximum lifetime or retained-state proof, telemetry, and removal release.

Use the smallest migration compatible with the actual lifetime and concurrency
contract:

| Format class | Required migration discipline |
| --- | --- |
| Request-local and never persisted | Atomic reader/writer replacement with fixed old/new behavior tests; no legacy decoder after the cutover commit. |
| Expiring or resumable across deployments | Dual-read for at least the maximum lifetime plus rollback window; writer advancement and decoder removal are recorded separately. |
| Durable or shared by mixed-version processes | Three-release rolling migration unless an exact topology record proves mixed readers/writers cannot coexist. |
| Build-time deterministic artifact regenerated before use | Version/digest bump plus old-artifact rejection or explicit adapter; no runtime dual reader unless retained artifacts are supported. |

Pre-1.0 status does not waive durable-state safety, but it also does not justify a
three-release decoder for a value that provably cannot survive a deployment.

Maintain `docs/v0.8-format-registry.json` as the checked-in registry for every
signed envelope, cursor, digest, admission record, deployment artifact, and
durable runtime record. Each entry names its writer versions, reader versions,
maximum lifetime, migration phase, key/purpose namespace, telemetry, rollback-safe
release, and decoder-removal release. Upgrade tests must be restart-safe at every
committed migration boundary; rollback tests must prove that the documented
previous version can still read all state written during the rollback window.

**Exit:** Maintained gateways/providers contain no independent cryptographic
envelope implementation, canonical bytes agree across runtimes, and admission has
one authoritative validator.

## Phase 4 — callable provider injection

Adopt this golden path:

```ts
const provider = application.inject(
  AcquisitionProvider.named("primary"),
);

await provider.acquire(input);
```

Required semantics:

- `application.inject()` returns a typed callable provider handle/proxy, not an
  inert descriptor and not a live build-time client.
- The handle remains compiler-visible, serializable, and runtime-hydrated.
- Extracted operations are stable bound function handles; arbitrary JavaScript
  `this` behavior is not part of the contract.
- Qualification, target/profile selection, graph identity, credentials,
  readiness, network access, and topology are framework-managed.
- Provider-private stores, clients, cancellation state, and credentials are
  injected behind provider construction.
- Only workloads that use the provider receive its configuration and credentials.
- Operation requirements are derived from the statically reachable managed
  closure graph. Merely selecting or placing a provider for the application must
  not force every generated execution family to hydrate all of its operations.
  Conversely, a reachable operation without exact public runtime metadata fails
  closed rather than degrading into placement-only behavior.
- Captured or returned provider methods propagate their dependency through
  modules, HTTP handlers, operations, processors, tasks, workflows, schedules,
  actors, and generated workers.
- Portable package-authored metadata makes external compiled packages first-class
  compiler inputs without namespace privilege or application wrapper glue.
- Remove application imports of internal provider-runtime modules after the
  compatibility path is qualified.

### Per-execution-family callable-provider qualification

Qualify one execution family at a time. Every family must pass the same portable
fixture before it is recorded as integrated; a direct in-repository call alone is
only characterization evidence.

| Required proof | Workflow/task slice | Failure that must be rejected |
| --- | --- | --- |
| Clean external package | A packed fixture exports the provider contract and a public static runtime operation without workspace-hoisted dependencies | Missing runtime operation, undeclared dependency, internal-only export, or path traversal |
| Authored call shapes | Direct `application.inject()` call, extracted bound operation, and a call through a module-local helper all resolve to the same qualified provider | Dynamic provider identity, unbound method behavior, or metadata loss through helper indirection |
| Reachability and coexistence | Only operations reachable from the managed closure become runtime requirements; unrelated selected or placement-only providers coexist without contaminating the worker | Global provider/profile metadata forcing an unrelated handler to hydrate an operation, or a reachable placement-only operation being silently accepted |
| Generated hydration | The workflow worker imports only the declared public runtime operation and injects it at the exact captured binding path | Replaying authoring-time `application.inject()`, `profile()`, or `provide()`, or importing an internal provider runtime |
| Graph and placement | Provider, access, network, readiness, and credential edges reach exactly the consuming workflow worker | Credentials or network access on unrelated workloads, missing provider edge, or ambient privilege |
| Durable semantics | Admission, causal identity, idempotency, retry, cancellation, lost-response reattachment, and task transaction behavior are unchanged | A second workflow run/effect, fabricated principal, dropped cancellation, or non-reattachable result |
| Reproducibility | Emitted source, plan, dependency metadata, and packed-consumer result are deterministic | Source-order-dependent bindings, ambiguous callback roots, or workspace-only success |

The workflow/task slice exits only when all six rows have positive and negative
evidence. Other execution families use the same rows with their own lifecycle
semantics substituted for the durable-workflow row. This matrix supplements the
global `PI-1` packet; it does not create a workflow-specific provider mechanism.

**Exit:** Clean package consumers use callable injected providers through every
maintained execution family with exact dependency and credential lowering.

## Phase 5 — complete execution-family convergence

### Scheduling

- Make imported `schedule(parameters, closure)` the public golden path.
- Use one definition/instance/occurrence model for fixed, dynamic, recurring,
  immediate, and one-time execution.
- Lower compatible workflow crons and future task/workflow execution through the
  shared schedule graph.
- Keep processor schedule convergence internal.
- Keep raw Kubernetes image/command scheduling as an explicitly named
  infrastructure escape hatch.
- Qualify deterministic local, bounded Kubernetes, shared Hatchet, and EventBridge
  Scheduler providers against the same portable contract.

The shared schedule graph and durable occurrence/lease record are the semantic
authority. Provider-native schedules are convergent delivery projections. A
provider may calculate or transport a due occurrence, but it may not become a
second authority for definition identity, desired revision, overlap, misfire,
authorization, or terminal receipts.

The maintained hosted-provider shape is therefore:

```text
canonical schedule definition + desired instance
  -> provider projection/convergence
  -> bounded provider delivery envelope
  -> canonical Applik8s occurrence admission
  -> generated application execution boundary
  -> durable occurrence/result receipt
  -> provider acknowledgement
```

Hatchet, EventBridge Scheduler/SQS, and Kubernetes CronJob adapters must carry
the same canonical occurrence identity and scheduled time into that boundary.
They do not execute captured application closures inside an unrelated provider
worker merely because that provider has a worker runtime. If a provider requires
a generated delivery worker, it contains only transport/admission machinery and
the minimum provider credential; callable application dependencies, model/event
runtimes, and their Secrets remain on the generated application execution
boundary. A crash after durable admission but before provider acknowledgement
must redeliver to the prior receipt rather than execute a second effect.

Maintain an executable scheduling semantic matrix covering every accepted source
surface and provider. Each applicable row records:

| Semantic dimension | Required portable meaning |
| --- | --- |
| Definition identity | Stable identity derived from the authored schedule definition, independent of provider names. |
| Instance identity | Stable identity for a dynamic/product-configured schedule and its current desired revision. |
| Occurrence identity | Deterministic occurrence key reused across retry, redelivery, and lost-response recovery. |
| Admission | Framework scheduler service principal, exact operation identity, canonical trusted context, and preserved causation; never the configuring user's ambient authority. |
| Time | Explicit timezone/calendar interpretation and provider-independent scheduled-at/started-at timestamps. |
| Overlap and fencing | Declared allow/forbid/replace policy with durable lease or provider guarantee sufficient to prevent stale execution. |
| Misfire and catch-up | Explicit skip/latest/all-with-bound semantics; never provider-default drift. |
| Retry and dead letter | Stable attempt identity, bounded retry policy, observable terminal failure, and provider-neutral receipt. |
| Pause, update, and cancel | Defined effect on future occurrences and already admitted work, including revision fencing. |
| History and observability | Correlation, trace, receipt, attempt, result, and failure records with the same public interpretation across providers. |
| Lifecycle | Owner, retained state, deletion ordering, rollback behavior, and leak-free teardown. |

Provider lowering must preserve the authored cadence exactly. A provider that
cannot represent a fixed interval, calendar, timezone, overlap, or misfire policy
fails before mutation with a stable compatibility diagnostic. In particular,
five-field cron adapters must not approximate second precision, non-divisor
minute/hour intervals, or multi-day fixed intervals with a calendar expression
that fires at a different cadence.

The source surfaces have the following required disposition. This table prevents
API similarity from being mistaken for semantic equivalence.

| Existing source surface | v0.8 disposition | Required preservation or rejection |
| --- | --- | --- |
| Imported `schedule(parameters, closure)` | Public golden path backed by the shared schedule graph | Full portable matrix, callable dependency discovery, canonical admission, and provider-neutral receipts |
| Static workflow cron | Lower to a shared schedule definition that starts the named workflow | Workflow run identity and durability remain workflow-owned; compilation rejects cron semantics the selected scheduler cannot preserve |
| One-time or delayed workflow start | Represent as one schedule occurrence when durable future admission is requested | Preserve workflow idempotency, causation, cancellation, and lost-response reattachment; immediate starts remain ordinary workflow calls |
| Dynamic `reconcileSchedule()` | Retain as the framework convergence mechanism for product-configured schedule instances | Stable instance identity, desired revision fencing, pause/update/delete semantics, and ownership must map exactly to the shared graph |
| Stream-processor schedule convergence | Keep internal to processor lifecycle while reusing portable scheduling machinery where exact | Checkpoint, partition, retry, and consumer ownership remain processor semantics and must not leak into the public schedule API |
| Actor alarm | Explicitly outside the public schedule graph | Alarm authority, actor identity, persisted timer state, and single-actor ordering remain actor-owned |
| Raw Kubernetes image/command cron | Explicit infrastructure escape hatch | Never presented as function-native parity; target-specific limitations and lifecycle are documented and diagnosed |

No source surface is removed merely to make the implementation uniform. First
prove a compatibility lowering, ship the migration path, and remove obsolete
syntax only at its recorded removal release.

Kubernetes cron resources, workflow crons, one-time workflow starts, dynamic
reconciliation, and processor convergence may share the graph only for semantic
cells they can preserve. Actor alarms remain outside this matrix except for
shared low-level utilities; their public authority and timer semantics stay
actor-owned.

### Actors

- Close remaining external alarm-cancellation authority gaps.
- Preserve exact connection, message, nested call, and alarm authority.
- Qualify deploy, rolling update, pod loss, reassignment, state recovery, drift
  repair, realtime reconnection, alarm delivery, and lifecycle teardown.
- Rerun the Kubernetes actor lifecycle after safely removing stale project/test
  workloads that consume OrbStack capacity.
- Keep relational journals, immutable evidence, and workflow history authoritative
  where required by the domain.

**Exit:** Schedule and actor public APIs expose one coherent semantic model and at
least the providers required by their scorecard maturity have live evidence.

## Phase 6 — finish the v0.8 capability matrix

Complete and qualify the existing work rather than adding unrelated public APIs:

- canonical application plan and diff;
- inferred least-privilege runtime access;
- persistent local supervisor and independent development environment;
- provider-neutral OpenTelemetry and target-native exporters;
- immutable lakehouse publication and queries;
- local, Kubernetes, AWS-local, and AWS deployment targets;
- TypeKro/Alchemy dependency and lifecycle ownership;
- target-selected provider guarantees; and
- migration, security, performance, cost, and failure diagnostics.

Every target consumes the same semantic graph. Differences live in provider
guarantees and lowerings, not domain-source branches.

Phase 6 is executed as the following bounded packages. A package may proceed as
soon as its prerequisites in the reviewable-work-package table pass; “Phase 6”
is not permission to create one cross-repository mega-diff.

### 6A. Canonical graph, plan, and diff (`GP-1`)

- Make graph provenance and graph digest stable across discovery order, helper
  boundaries, generated-source regeneration, and clean package consumption.
- Produce one canonical, redacted application plan with explicit requirements,
  providers, artifacts, authority boundaries, ownership, and target-compatibility
  findings.
- Make plan diff classify semantic create/update/replace/delete/no-op changes and
  refuse comparison across incompatible graph or format versions.
- Keep provider-native object details behind typed target-plan facets rather than
  leaking them into the semantic graph.

**Exit:** The GuestBook, Chirp, and Agentic Start graphs reproduce byte-for-byte,
their plan diffs are stable, and incompatible target semantics fail before
mutation with named diagnostics.

### 6B. Inferred runtime access (`RA-1`)

- Lower semantic dependency, operation, data, secret, network, tenancy, and target
  requirements into least-privilege access for each claimed target.
- Intersect inferred requirements with selected provider guarantees; never treat
  a provider default or ambient cluster/account permission as evidence.
- Prove both allowed behavior and denied undeclared behavior, including
  cross-namespace, cluster-scoped, cross-tenant, secret, broker, object, lakehouse,
  and provider API access.
- Keep access-policy output stable and explainable in the application plan.

Execute this capability as four reviewable boundaries:

1. `RA-1a` defines the canonical semantic requirement/policy and intersects it
   with selected provider guarantees.
2. `RA-1b` isolates local host input and projects compiler-authored framework
   credentials only to the exact consuming execution identity.
3. `RA-1c` materializes the same contract into target resources. First qualify
   deterministic pre-mutation lowering (`RA-1c1`), then Kubernetes
   RBAC/NetworkPolicy/Secret placement (`RA-1c2`), then AWS IAM/security-group/
   secret placement (`RA-1c3`). A target adapter may translate provider limits;
   it may not invent a parallel access model.
4. `RA-1d` proves intended allows and denials, policy narrowing after a source
   change, drift repair, ceilings, and provider-limit diagnostics at each claimed
   fidelity tier. Deterministic, OrbStack, AWS-local, and real-AWS evidence remain
   separately labelled.

Each boundary must name its compiler-owned source contract, target lowering,
preflight, denial fixture, cleanup authority, and unsupported/provider-limit
diagnostic. No live test may compensate for a target plan that does not fail
closed before mutation.

**Exit:** Exact IAM/RBAC/network/credential plans contain no unexplained wildcard
or ambient privilege, and negative live or fidelity tests fail at the intended
authority boundary.

### 6C. Persistent local runtime (`LR-1`)

- Use the production graph, admission, scheduling, actor, provider, persistence,
  and access contracts rather than maintaining a second “dev-only” semantic
  runtime.
- Make the supervisor persist owned process/resource state, recover after crash,
  reconcile source changes, report stable diagnostics, and reset or teardown
  without leaks.
- Preserve fast local hot reload and filesystem aspects as target-specific
  development behavior without changing application source.

**Exit:** A freshly packed generated application can start, reload, survive
supervisor/process failure, restart, reset, and teardown through one documented
local journey.

### 6D. Observability (`OB-1`)

- Carry correlation, causation, principal class, operation, definition/instance/
  occurrence or actor identity, attempt, and provider identity through one
  provider-neutral telemetry contract.
- Apply one redaction policy before exporters see attributes; never expose tokens,
  secrets, raw trusted context, or tenant data merely because an exporter accepts
  arbitrary attributes.
- Qualify local collector, Kubernetes backend, external OTLP, and CloudWatch
  independently. Telemetry remains evidence and never becomes correctness state.

**Exit:** Cross-boundary traces join correctly, failure/retry/denial events have
stable semantics, and each advertised exporter has exact live evidence.

### 6E. Immutable lakehouse (`LH-1`)

- Define atomic publication around immutable object identity and a committed
  manifest/receipt; incomplete uploads and broker deliveries cannot become
  query-visible authority.
- Preserve schema/version, partition, tenancy, causation, replay, idempotency,
  retention, compaction, and deletion semantics across DuckDB and AWS lowerings.
- Keep query engines and catalogs rebuildable from the publication authority.

**Exit:** Provider-differential queries agree, interruption/replay is idempotent,
and real Athena/Glue/S3 lifecycle and representative cost evidence exists before
the AWS lakehouse row is advertised stable.

### 6F. Target and lifecycle parity (`TP-1`)

- Lower the same graph to local, AWS-local, AWS, and Kubernetes while respecting
  the semantic authority map and the target compatibility matrix.
- Delegate Kubernetes resource ordering, ownership, readiness, replacement, and
  teardown to maintained TypeKro/Alchemy contracts rather than recreating a
  shadow deployment engine in Applik8s.
- Treat MiniStack as AWS API-fidelity evidence only; keep real AWS lifecycle,
  IAM, networking, encryption, observability, drift, and cost qualification
  separate.
- Make unsupported provider guarantees fail closed during planning.

**Exit:** Target plans are traceable to one graph; each stable row has lifecycle,
drift, security, and cleanup evidence at the exact claimed tier.

### 6G. Development agent and diagnostics (`DX-1`)

- Give setup, inspect, diagnose, explain-plan, repair guidance, and verification
  stable machine-readable contracts and public package boundaries.
- Diagnose missing providers, credentials, capacity, controller versions,
  permissions, incompatible target guarantees, drift, and leaked ownership before
  suggesting mutation.
- Test clean generated applications and deliberately broken fixtures; guidance
  must point to the public golden path rather than internal package surgery.

**Exit:** The development-agent gate reproduces correct diagnoses and safe repair
guidance for both successful and adversarial journeys.

### 6H. Migration and security (`MS-1`)

- Exercise previous-release readers/writers, retained state, interrupted upgrade,
  restart-safe resume, rollback, key rotation, authority revocation, and cleanup
  for every changed durable format or lifecycle contract.
- Run secret canaries and provenance tests through generated source, logs,
  telemetry, plans, images, status, object storage, and provider configuration.
- Fail closed on unregistered compatibility adapters, private cryptography,
  private admission shapes, or ownership ambiguity.

**Exit:** The documented previous release can recover all rollback-window state,
and every compatibility branch has evidence, telemetry, an owner, and a removal
release.

### 6I. Performance, scale, and cost (`PC-1`)

Record reproducible baselines before optimizing and preserve history as evidence,
not as a one-off release note. The scorecard must define explicit ceilings or
regression percentages for:

- compiler wall time and peak memory for GuestBook, Chirp, and Agentic Start;
- generated JavaScript, WASM component, operator image, and browser bundle size;
- cold start and steady-state handler latency;
- bounded-concurrency throughput and backpressure behavior;
- database connection/pool pressure and durable-store contention;
- stream consumer scaling, retries, and redelivery;
- local supervisor idle/active memory;
- Kubernetes steady-state requests/limits; and
- representative AWS plan and observed test-fixture cost.

A regression beyond an accepted budget blocks the relevant maturity claim unless
the maintainer accepts a documented tradeoff. Performance gates use fixed fixtures,
warmup rules, multiple samples, and noise-tolerant statistics; a single timing
assertion is not release evidence.

Capture the unoptimized baseline before changing the measured implementation.
For every metric, the scorecard records the fixture, machine or environment
class, warmup, sample count, aggregation method, absolute ceiling, relative-
regression ceiling, and variance policy. A gate fails on either the absolute or
relative ceiling. Changing a fixture or environment starts a new comparable
series rather than rewriting history.

**Exit:** Every advertised budget has a versioned fixture and comparable history;
absolute or relative regressions either pass, block the affected claim, or carry
an explicit maintainer-approved tradeoff.

Each workstream closes through the existing machine-readable gate rather than a
subjective phase-level declaration:

### Live-environment preflight

Before any long-running OrbStack, Docker, MiniStack, or cloud gate, run a bounded
preflight that verifies:

- expected context/account and explicit opt-in;
- node pod, CPU, memory, and storage capacity;
- required StorageClass, controllers, CRDs, and compatible versions;
- Docker, registry, image, network, and DNS availability;
- required provider configuration is present without printing secret values;
- absence of conflicting fixed-name test installations; and
- ownership metadata needed for lifecycle cleanup.

Preflight fails before mutation with actionable diagnostics. Cleanup uses the
owning Alchemy/TypeKro/application lifecycle and verifies absence; raw Kubernetes
deletion is emergency repair evidence, not the ordinary path.

## Phase 7 — product and example qualification

- **GuestBook:** readable minimum golden path.
- **Chirp:** distributed composition, streaming, access, object, lifecycle, and
  scale pressure.
- **Agentic Start:** polished product framework exercising identity, tenancy,
  billing, Stripe, usage, entitlements, search, agents, approvals, artifacts,
  evaluations, schedules, actors, and the Builder evidence surface.

Required evidence includes fresh generation, clean package consumption, local
startup/hot reload, browser journeys, production bundles, OrbStack deployment and
teardown, target plan parity, provider differential tests, generated-file
reproducibility, package boundaries, and bundle-size ceilings.

No internal package import may be required by generated application source.

## Phase 8 — release qualification

- Synchronize all coordinated package versions.
- Pass packed-consumer and published-shape import tests.
- Qualify generated runtime images and dependency/container provenance.
- Pass runtime-integrity, local, OrbStack, MiniStack, browser, migration,
  security, performance, cost, product, package, Rust, and scorecard gates.
- Run real AWS CloudWatch, Athena, EventBridge Scheduler, IAM, networking,
  encryption, drift, lifecycle, and cost evidence before claiming real-AWS
  compatibility.
- Keep scorecard and acceptance flags false until their exact commands and live
  environments pass.
- Produce a final gap analysis and exact-commit attestation for maintainer review.

The final maintainer packet contains:

- the exact source commit and coordinated package/image versions;
- public API additions, removals, and migration guidance;
- the format registry and rollback window;
- scorecard results with links to deterministic and live evidence;
- known limitations and externally blocked claims;
- performance/bundle/cost comparison against the recorded baseline;
- clean-install and previous-release upgrade results; and
- proof that all live test resources were removed.

Do not tag or publish until the maintainer separately authorizes the release.

## Critical path

```text
checkpoint
  -> narrow v0.7.x workflow unblock
  -> rebase and deduplicate
  -> canonical JSON v1
  -> signed envelopes
  -> canonical admission
  -> callable provider injection
  -> schedule and actor qualification
  -> remaining target/provider qualification
  -> product acceptance
  -> release review
```

This is the minimum blocking path. After canonical admission integrates, provider,
schedule, actor, target, migration, and product lanes should progress independently
and converge at release qualification.

## Evidence discipline

- A passing contract test is not live provider evidence.
- A successful MiniStack run is not real AWS evidence.
- A local actor provider is not distributed actor evidence.
- A generated plan is not a successful deployment.
- A preview UI cannot substitute for a stable runtime gate.
- Cleanup is part of every live lifecycle test and must fail on leaks.
- External blockers remain visible; they do not justify weakening maturity labels.
